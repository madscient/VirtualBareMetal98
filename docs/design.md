# 設計

読者: 開発者・AI。方式と、その決定の理由・前提を書く。要件は [spec.md](spec.md)。

動かして確かめてあるのは、ディスクイメージ層（§8 の最下層）と、モニタ核のうち機種に依らない
部分（モード切替、例外の入口、割り込みの反射、ゲスト用メモリの写像、I/O トラップ）である。
それ以外は設計だけで、ハードウェアや CPU の振る舞いについての記述の確度は §12 にまとめてある。

## 1. 全体像

```
        ホスト世界                       モニタ                     ゲスト世界
   ┌───────────────────┐         ┌───────────────┐         ┌─────────────────────┐
   │ MS-DOS (リアルモード) │ ◀─切替─▶ │ 保護モード ring 0 │ ◀─例外─▶ │ 仮想 PC-98 (仮想86モード) │
   │  ファイル入出力        │         │  割り込みの反射   │  割込み  │  ベアメタルアプリ       │
   │  FDD BIOS の意味論    │         │  BIOS の横取り    │         │  実機の ROM BIOS      │
   │  ディスク交換メニュー   │         │  ページング       │         │                     │
   └───────────────────┘         └───────────────┘         └─────────────────────┘
        本来の下位 640KB              両方の世界の外に常駐          拡張メモリ上の別の 640KB
```

ホストの MS-DOS とゲストのアプリは、どちらも「下位 1MB を丸ごと自分のもの」として動く。
同じ番地を二者が使うので、ゲストには拡張メモリ上に別の 640KB を与え、ページングでそれを
下位番地に見せる。ホストの MS-DOS は元の場所に手つかずで残るので、イメージファイルの
読み書きにも、終了後のプロンプト復帰にもそのまま使える。

同時に走るのは常に片方だけで、切り替えはモニタが行う。

ゲストに見せる構成は PC-9801VM 相当（[spec.md](spec.md)）。ハードウェアは実物をそのまま使い、
差し替えるのは構成情報（§6）、スイッチの読み出し値（§15）、V30 固有命令の代行（§14）である。

## 2. 決定と前提

| # | 決定 | 理由 | 前提（崩れたら見直す） |
| --- | --- | --- | --- |
| D1 | ホスト世界は仮想86にせず、リアルモードに戻して走らせる | HIMEM やディスク BIOS、常駐物が特権操作や保護モードを使っても、何も仮想化せずに動く。モニタが面倒を見る対象がゲストだけになる | ホストがリアルモードで起動している。EMM の下（ホストが EMM の仮想86）では「ホストへ移る／戻る」の 2 手続きだけを VCPI 経由にする（§18） |
| D2 | ゲストは IOPL=3 の仮想86で動かし、I/O ポートは原則素通しにする | ベアメタルアプリは割り込みの禁止・許可や I/O を多用する。それを毎回トラップすると遅い。ゲストは 1 つだけで CPU を分け合わないので、割り込みフラグを仮想化する必要がない | ゲストが 1 つ。ホストとゲストが同時に走らない |
| D3 | BIOS の横取りは、ROM のエントリ先頭 1 バイトを HLT に差し替えた「写しページ」で行う（§5） | INT 命令で呼んでも、ベクタを読んで far call しても、ゲストが自前のフックを挟んでも、最後に ROM へ入る瞬間に捕まえられる | ROM エントリの番地が分かる（§6）。分からない機種では INT 命令の時点で横取りする方式に落とす |
| D4 | FDD BIOS の意味論はホスト世界の C で実行し、モニタはゲストのメモリとの複写だけを受け持つ | 論理の大半を、同じソースのままホスト OS 上で検証できる | BIOS 呼び出し 1 回につき世界の切替 1 往復、という所要時間が許容できる（未計測） |
| D5 | セクタデータの受け渡しは、ホストの下位メモリに確保した 64KB の転送バッファを介す | リアルモードのホストからはゲストのメモリ（拡張メモリ上）に届かない。INT 1Bh の転送長は 16 ビットなので、64KB あれば 1 回の呼び出しを 1 往復で済ませられる | — |
| D6 | イメージの管理情報は常駐させず、トラック単位で読む | NFD r0 のヘッダは 68KB あり、near データに収まらない | ホストのファイルアクセスが十分速い（HDD 上のイメージを想定） |
| D8 | 例外・割り込みの判断は ring 0 で動く C で書き、アセンブリはモード切替と入口・出口だけにする | 判断の部分が読みやすく、試験を足しやすい。アセンブリの量が減る | 保護モードのコード・データセグメントを、実行ファイルのそれと同じ場所を指す 16 ビットセグメントにしてあること（§4）。割り込み 1 回あたりに C の関数呼び出しが挟まる時間が許容できること（未計測） |
| D9 | 「PC-9801VM 相当」は、ハードウェアは実物のまま、ゲストから見える構成情報（BIOS ワークエリアの機種判別・装置フラグ、DIP スイッチの読み出し値、メモリスイッチ、拡張メモリ量）を揃えることで実現する | 表示や音の再現は仮想86モードでの直接実行と相容れない。PC-9801VM 向けのアプリは、その上位互換であるホストのハードウェアの範囲で動く | 対象アプリが、ホストにあって PC-9801VM にない機能の不在に依存しないこと。依存するものが出たら、該当する I/O をトラップして隠す |
| D10 | V30 エミュレーションは、V30 固有の命令が 386 で例外になることを利用して、例外のときだけ代行する（§14） | 命令単位の解釈実行にすると仮想86モードの速さが失われる。固有命令は使われる頻度が低い | 対象アプリが、例外にならない差（§14「直せない差」）に依存しないこと。ホストの CPU の世代によって届かない命令があることを受け入れること |
| D11 | ゲストの HLT は、ring 0 で本物の HLT を実行して次の割り込みを待ち、その割り込みを「HLT の次の命令」を戻り先にしてゲストへ渡す。割り込み禁止のままの HLT は、起こせる割り込みがないのでゲストの停止としてホストへ返す（ホストは VM メニューを開く。[spec.md](spec.md)） | 命令を進めずに戻す方式だと、割り込みのあとゲストが HLT に戻って再び止まり、「HLT で 1 回の割り込みを待つ」コードが先へ進まない。HLT を無視する方式だと待たずに進んでしまう | ring 0 で待っている最中の割り込み進入を、入口がスタックの位置で見分けられること（§4）。NMI は考えない |
| D7（見送り） | ゲスト世界の 0 番ページ（割り込みベクタと BIOS ワークエリア）だけを物理の 0 番ページに写像し、世界の切替のたびに入れ替える案 | BIOS を内蔵の実装で代行するエミュレータが BIOS ワークエリアを物理番地で読み書きするなら要る、と考えていた。NP21/W で確かめたところ、内蔵 BIOS（INT 18h AH=03h）の書き込みはページングを通ってゲスト側のメモリに入った（§12）。よって不要 | 他の BIOS 機能や別のエミュレータで物理番地の読み書きが見つかったら復活させる |

## 3. メモリとページング

ゲスト世界の線形アドレスの割り当て。

| 線形アドレス | 写像先 | 備考 |
| --- | --- | --- |
| 00000–9FFFF | ゲスト用に確保した拡張メモリ | 割り込みベクタと BIOS ワークエリアもここに入る |
| A0000–FFFFF | 同じ番地の実メモリ | VRAM と ROM は実物を共有する。横取り用に差し替えたページだけが RAM の写し。EMM の下でも物理番地どおりなので、EMM が UMB などを写しているページでは、ホストに見える中身と違う（§18） |
| 100000–10FFFF | A20 の状態に応じて、00000–0FFFF と同じページ／何もなし | A20 を閉じた実機と同じ折り返しを再現する |
| モニタ用の高位アドレス | モニタのコード・データ・GDT・IDT・TSS・ページテーブル | ゲストの 1MB の外に置き、ゲストからは見えない |
| （ゲストの番地ではない）XMS ブロックの 640KB より後ろ | ホスト側の大きな控え（`vbm.h` の `stash_*`。24KB） | ホストのテキスト画面とメニューの間のゲストの画面の控え。データセグメント（スタックと同居）に置かないため。XMS ドライバの転送で VRAM と直接写す。ring 0 からは使わない |

- ゲスト用メモリは XMS（HIMEM.SYS）があればそこから確保して固定する。なければ BIOS の拡張メモリ量から直接切り出す。確保経路は差し替えられる形にする（VCPI 用の 3 つ目が来る）
- モニタは 16 ビットのコードセグメントで書き、必要な箇所だけ 32 ビットのオペランドを使う。実行ファイルを 16 ビットの DOS プログラム 1 本にまとめるため

## 4. 割り込み・例外・特権命令

- IDT の全ベクタを 32 ビットの割り込みゲート（DPL=3）にし、ベクタ番号を積んで共通処理へ入る
- 共通処理は原則として「ゲストの割り込みベクタ表を引いて、ゲストのスタックに FLAGS・CS・IP を積み、そこへ飛ばす」。ハードウェア割り込みもソフトウェア割り込みも同じ扱い
- PC-98 では IRQ のベクタ（08h–17h）が CPU 例外の番号と重なる。仮想86モードからの進入は必ず同じスタック位置から始まるので、エラーコードが積まれているか（＝スタックの深さ）で例外と割り込みを見分ける
- 進入の形は 3 つ: 仮想86モードからのエラーコードなし／あり、そして ring 0 で HLT 待ちの最中（D11）。いずれもスタックの位置で見分ける。それ以外の位置から来たものはモニタ自身の例外として扱う
- 一般保護例外で扱うもの: HLT（割り込み待ち、または §5 の横取り印）、トラップ指定した I/O ポート、V30 固有命令のうち 386 では特権命令に当たるもの（§14）、DPL=0 のゲートへの INT n（§14）。それ以外は異常としてゲストを止めて報告する
- 未定義命令例外（ベクタ 6）: V30 固有命令なら代行する（§14）。それ以外はゲストの INT 6 へ反射する
- ゼロ除算例外（ベクタ 0）: `-v30 on` では戻り番地を V30 の規則に直して反射する（§14）
- モニタ自身の実行中に例外が起きたら、状態を表示して MS-DOS に戻る

ring 0 で動く C には制約がある。守られないと保護モードで例外になるが、リアルモードでは
何も起きないので、ビルド時に検査する（`tools/build16.sh`）。

- 名前が `_r0.c` で終わるファイルに置き、保護モード向けの設定（`-mprotected-mode`）でコンパイルする。
  通常の設定で gcc-ia16 が出すコードは、セグメントレジスタを値の置き場として使う
- C ライブラリとコンパイラの補助関数（32 ビットのシフト・乗除算、構造体の複写が化ける `memcpy` など）を
  呼ばない。外部への参照は `mon_` で始まる名前だけにする
- far ポインタを使わない。ゲストのメモリは線形番地を指定する補助関数で読み書きする

C から呼ぶアセンブリの関数は、gcc-ia16 の規約に合わせて SI・DI・BP・ES を保存する
（ES は「呼ばれる側が保存するレジスタ」で、コンパイラが呼び出しをまたいで値を置く）。

トラップする I/O ポート（最小限）:

| ポート | 目的 |
| --- | --- |
| CPU リセット | 仮想マシンの再起動として扱う（§10） |
| A20 制御 | §3 の折り返しを切り替える |
| キーボードのデータ・ステータス | ホットキーの検出と、モニタが先に読み取った値の再提供（§9） |
| DIP スイッチの読み出し | 設定された値を返す（§15） |
| テキスト表示まわりの書き込み専用レジスタ | 値を控えておき、メニューを閉じるときに戻す（§9） |

## 5. BIOS 呼び出しの横取り

ROM BIOS のエントリがあるページを RAM に写し、エントリ先頭の 1 バイトを HLT に書き換えて、
ゲスト世界ではその写しを見せる。ゲストがそこへ来ると一般保護例外になるので、番地が登録済みの
横取り印と一致すればモニタが処理する。処理後は、ゲストのスタックに積まれている割り込みフレームを
使って呼び出し元へ戻す。

横取りの対象:

| 対象 | 処理 |
| --- | --- |
| INT 1Bh（ディスク BIOS） | デバイス種別がフロッピーならイメージで応える（§8）。HDD の種別には、SASI / IDE（0・8）なら「準備できていない」（60h）、SCSI など（2・A・C）なら「装置なし」（40h）を返す（ホストの HDD は見せない。`fdbios.c`。参考実装に合わせた値で、実機の BIOS がつながっていない装置に何を返すかは未確認。実機の報告で、FreeDOS(98) のゲストが SASI の HDD を探し続けている。worklog の残作業 6） |
| リセットベクタ FFFF:0000 | 仮想マシンの再起動（§10） |
| INT 1Fh のうち保護モードを使う機能 | 拡張メモリは見せないので、機能ごと失敗を返す |

横取りの表は、線形番地と識別子の組を並べたもの（`mon_hook_add`。上限は定数）。登録のない HLT は
本物の HLT として扱う（D11）。

いまの実装（`src/dos/vbm98.c`）は、INT 1Bh については ROM のエントリではなく、ゲストのベクタ表の
1Bh を HLT で埋めた 4KB のページ（横取り印のページ）へ向けている。ROM エントリの番地に
依存せず、どの機種でも同じに動くため。ROM エントリを far call で呼ぶアプリには効かない。
D3 の方式（ROM の写し）に切り替えるかは、そういうアプリが見つかってから決める。リセットベクタは
D3 のとおり ROM の写しで横取りしている。

横取り印のページを置く番地は起動時に決める（`pick_hook_seg`）。C0000h〜DFFFFh（拡張 ROM の領域）を 4KB ずつ見て、
ホストに何も載っていない（全部 FFh に読める）ページのうちいちばん上を使い、`-sbrom` を置く範囲は避ける。
見つからなければ BASIC ROM 領域の末尾（F7000h）に置く。F7000h を避けるのは、ROM の BASIC を使うゲスト（ディスク版の
N88-BASIC など）からその 4KB が見えなくなるため。起動時に領域の様子と選んだ番地を表示する。
前提と限界: 空いて見えるページを、ゲストがあとから有効にするハードウェア（バンク切替の ROM など）が使うことは
ないとみなしている。このページはゲストから書ける RAM なので、上位メモリを書き込みで調べて使おうとするゲスト
（UMB を作るメモリマネージャなど）は横取り印を壊しうる。確認済み（NP21/W、DOSBox-X）: どちらも DF000h が選ばれ、
INT 1Bh がそこを通り、F7000h には元の内容が見える（`run_dos_tests.py boot`）。F7000h に置く経路は開発用の
`-hookseg F700` で通している（`boot2dd`）。実機（PC-9821Cr13）でも DF000h が選ばれ、v0.1.1 で止まっていたディスク版の
N88-BASIC(86) が v0.1.2 で起動した（利用者の報告）。ただし同じ版で拡張メモリ量とベクタの扱いも変えているので、この
変更が効いたのかは切り分けていない。

## 6. ゲストの初期状態

ゲストには「電源投入後、IPL に入る直前」の PC-98 を見せる必要がある。ところがホストは MS-DOS が
動いている状態で、割り込みベクタの一部は MS-DOS やドライバ（RAM 上のコード）を指している。
ゲストの 640KB にそのコードは存在しないので、そのままは渡せない。

割り込みベクタ（256 本とも同じ規則で決める）:

1. ホストのベクタが本体の ROM（E8000h〜FFFFFh）を指していれば、そのまま使う
2. RAM を指している場合、ROM のエントリを突き止められたらそれを使う。方法は、ホスト世界で
   その割り込みを無害な機能番号で 1 回呼び、シングルステップで追って最初に ROM へ入った番地を採る
3. 突き止められなければ、ROM 内の IRET 1 バイトを指す。それが IRQ のベクタなら、ゲストの
   割り込みマスクの初期値でその IRQ を閉じる

ROM の入口の追跡（規則 2。`src/dos/romtrace.S`、`vbm98.c` の `guest_memory`）:

- 対象は 08h（タイマ）・09h（キーボード）・0Ah（VSYNC）と、BIOS のサービスの 18h・19h・1Ah・1Ch。ROM の BIOS が
  自分でハンドラを持ち、ゲストが BIOS 経由で使うもの。1Bh は自前で処理する（§5）。1Fh は対象にしない（拡張メモリを
  使う機能があり、ゲストには拡張メモリを見せないので、ROM へ渡さず印のままにする）。ほかのハードウェア割り込みは、
  使うゲストが自分でハンドラを置く
- 起動時に 1 回、ホスト世界で、対象のうち RAM を指しているベクタのハンドラを AX = FF00h（どの機能でもない値）で
  シングルステップ（TF）しながら呼ぶ。実行が RAM から ROM へ移るたびに、そこが割り込みの入口として使える入り方かを
  確かめ、使えるなら入口として記録する
- 「最初に ROM に入った番地」をそのまま入口にはしない。ホストのハンドラは ROM の途中へ飛び込むことがあり（下の (c)）、
  その番地をゲストのベクタにすると、ゲストの割り込みのたびにスタックが壊れる。入口と認めるのは次の 3 とおり
  - (a) far jmp でつながる鎖: スタックがハンドラに入ったときのまま（割り込みのフレームがそのまま載っている）
  - (b) pushf + far call: スタックの先頭が、直前に実行した命令のすぐ後ろ（1〜16 バイト先、同じセグメント）を指す
    戻り番地で、その下の語が FLAGS として読める（bit 1 が 1、bit 3・5・15 が 0）うえに演算フラグがいまの値と同じ
  - (c) NEC の MS-DOS の INT 1Ah: IO.SYS は ROM の入口の 3 命令（sti / push ds / push dx）を自分で実行してから
    「入口 + 19h」へ far jmp する。ベクタが 1Ah で、スタックに 2 語積まれていて、入った番地 − 19h に FB 1E 52 が
    あれば、番地 − 19h を入口にする
- ROM のコードは実行しない。(a) と (c) では、そこでハンドラを打ち切って戻る（ROM が戻る先は追跡器なので、ROM が
  何もせずに戻ったのと同じ）。(b) では戻り先を自前の IRET に差し替え、ホストのハンドラの残り（元を呼んだあとの
  後始末）を最後まで走らせる。ホストのハンドラ自身は 1 回走る
- 入口と認めない入り方（ROM の途中への飛び込み、ROM のサブルーチンの呼び出し）なら、ROM のコードをそのまま
  実行させて追い続け、RAM に戻ったあとの次の機会を待つ。認めなかった最初の番地と、そのときスタックに積まれていた
  バイト数を起動時に表示する（`INT xxh enters the ROM at ...`。未知の横取りの形を実機の報告から知るための材料）
- 追うのは far jmp / far call でつながる鎖だけ。ハンドラの中の INT 命令の先は追わない（INT は TF を落とす）ので、
  別の割り込みの ROM の入口を取り違えない
- 規則 1 の判定（`vbm98.c` の `in_rom`）: そのまま使うのは、本体の ROM がある E8000h〜FFFFFh を指すベクタだけ。
  それより下（下位メモリ、VRAM、UMB、C0000h〜DFFFFh の拡張 ROM）と HMA を指すベクタは、ホストのものとして
  規則 2・3 で扱う。拡張 ROM はゲストからも同じ中身で見えるが、そこにあるのはホストの装置（ディスクのボードなど）の
  ハンドラなので、印にして IRQ を閉じる扱い（下の「ホストの IRQ」）に合わせる。サウンド BIOS の ROM を指すベクタ
  （INT D2h など）もゲストには渡らない
- E8000h 以上でも、EMM ドライバが別のメモリを写しているページ（§18）は、書けるならホストの RAM として扱う。
  MS-DOS 6.2 の EMM386.EXE は `/HIGHSCAN` を付けると BASIC ROM の領域（E9000h〜F3FFFh）にも UMB を作り、`LH` や
  `DEVICEHIGH` で読み込んだ常駐物がそこに入る（§12）。ゲストにはその番地の実物が見えるので、そこを ROM とみなして
  ベクタを渡すと、ゲストは ROM の無関係な所へ飛ぶ。書けるかどうかは、反転した値を書いて読み返して決める（値は
  戻す。`romtrace.S` の `rom_writable`。C では書かない。§12）。番地どおりのページは書いてみずに ROM とみなす:
  BIOS のハンドラがある番地に書くと書いた値が読める環境があり（DOSBox-X と NP21/W がそう。§12）、そこで
  書いてみると、BIOS を指すベクタを RAM と取り違える
- 写し替えられていて書けないページ（E8000h 以上）は、ROM の写しとみなしてベクタをそのまま使う。本体の ROM の
  写しを同じ番地に置いているだけなら正しいが、別のものなら、ゲストはその番地の実物へ飛ぶ。どちらなのかは見分けて
  いないので、該当するベクタを起動時に `note: vectors into read-only memory the EMM driver remapped ...` の行で
  知らせる（そういう構成があるかは未確認）
- 入口の追跡（`romtrace.S`）が、鎖をたどる途中の番地を見る基準: A0000h 未満と HMA は RAM、E8000h 以上は ROM
  （写し替えられたページは書いてみて決める）、その間（UMB、拡張 ROM）は書いてみて、書ければ RAM。UMB に載った
  常駐物は RAM として通り抜け、拡張 ROM に入ったら ROM に入ったものとして扱う
- 4000 回数えても入口が見つからなければ追うのをやめ（ハンドラは普通に最後まで走る）、そのベクタは規則 3 になる
- 起動時の表示に、印へ向けたベクタ（`redirected:`）と、突き止めた入口（`traced to their ROM entries:`）を出す。
  入口には、認めた入り方を `(a)`・`(b)`・`(c)` で添える
- 追跡の対象なのに入口を突き止められなかったベクタは、`warning: INT xxh is hooked in the host ...` の行で知らせる。
  ゲストでは何もしない印になるので、18h ならキー入力も画面の制御も効かなくなる。黙って起動すると、原因が分からない
  まま操作できなくなる（実機の報告: INT 18h を横取りする常駐物 AUTOMATE、30 行 BIOS のどちらでも、ゲストでキーが
  読まれずキーバッファがあふれた。追跡できなかった理由は未確認で、その常駐物を入れた再現はしていない）

前提と限界:

- 追跡の対象のベクタが、拡張 ROM（E8000h 未満の書けない番地）を直接指しているホストは扱えていない。ホストの
  ものとして追跡にかけるが、追跡は RAM から始まる前提なので、入口を取り違えるか、見つけられない（コードを
  読んだ見立て。そういうホストがあるかは未確認）
- ホストのハンドラが AX = FF00h の呼び出しを ROM まで渡すこと。機能番号を見て自分で処理して戻るハンドラ、条件に
  よって ROM を呼ばないハードウェア割り込みのハンドラ、(a)〜(c) のどれでもない入り方をするハンドラでは
  突き止められず、規則 3 になる
- 入口と認めなかった場合と、上限まで追った場合は、ROM のハンドラが AX = FF00h で実際に 1 回走る。未定義の機能番号を
  ROM が無視することを当てにしている（推測。実機の ROM では未確認）
- (b) の判定は経験則。pushf を使わずに FLAGS の語を積んで far call するハンドラは入口と認めない（規則 3 になる）。
  逆に、ROM のサブルーチン（RETF で戻るもの）を、たまたま FLAGS と同じ語を積んだ状態で far call するハンドラが
  あれば取り違える
- (c) は IO.SYS の動きから ROM の入口の形を逆算している。実機の ROM の入口が同じ 3 バイトで始まるかは未確認で、
  違っていれば (c) は成り立たず規則 3 になる（ゲストが壊れる側には倒れない）
- ホストのハンドラが ROM の前後でしていた仕事（キーの読み替え、常駐物の処理）はゲストでは起きない。それが電源
  投入直後の姿でもある
- ホストのハンドラを要求のないまま 1 回呼ぶので、キーボードのハンドラがデータポートを読み直して、ホストのキー
  バッファに 1 文字入ることがありうる（起きるかどうかは未確認。試験では見ていない）

ホストの IRQ（`guest_memory`、`held_imr_m` / `held_imr_s`）: ホストの RAM のハンドラが受け持っている IRQ（印に向けた
08h〜17h のベクタ）は、ゲストの割り込みマスクの初期値で閉じる。ディスクのボードのように、ホストだけが使う装置の割り込みが
これに当たる。開けたまま印で受けると、割り込みコントローラには EOI が出るが装置側の要求は片付かない。PC-98 の割り込み
コントローラは立ち上がりで反応するので、要求が出たままだと以後その IRQ が来なくなり、ホストに戻ったあとのディスク
アクセスが止まる。閉じておけば、来た割り込みは保留され、ホストに戻ってマスクを戻した時点でホストのハンドラに届く。
閉じないもの: キーボード（マスタの IR1。モニタがホットキーをこの割り込みで拾う）と、マスタの IR7（スレーブの中継。
閉じるとスレーブ側の割り込みが全部止まる）。ゲストが自分でハンドラを置いてマスクを開けたら、ゲストの設定に従う。
リセットでも同じ初期値に戻す。前提と限界: ホストとゲストが同じ IRQ を同じ時間帯に別々のハンドラで必要とする使い方
（ゲストの実行中もホストの常駐物が割り込みで動き続ける必要がある装置）は扱えない。割り込みが来るたびにホストへ
切り替える仕組みが要る。確認済み（DOSBox-X、NP21/W）: 常駐プログラムがスレーブの IR1（ベクタ 11h）を横取りすると、
ゲストから見た割り込みマスクのそのビットだけが立つ。入口を追えない形でキーボードを横取りしても IR1 は開いたまま
（`run_dos_tests.py hook`）。保留した割り込みがホストに戻ってから届くことと、実機（PC-9801BX の SCSI のボード）で
ディスクが止まらなくなるかは未確認。

20h 以上のベクタ（`guest_memory`）: ホストの DOS や常駐物のほか、以前に動いたソフトの残り物が入っている。本体の ROM を
指すものはそのまま渡す。0000:0000（未設定）もそのまま渡す。それ以外、つまりホストの RAM や拡張 ROM を指す
ものは、横取り印のページに置いた IRET 1 バイト（+300h）へ向ける（判定は上の `in_rom`）。そのまま渡すと、ゲストがその割り込みを出したとき、
中身のないゲストの RAM へ飛ぶ。向けた本数を起動時に表示する（`vectors 20-FF into host RAM, pointed at an IRET:`）。
前提と限界: 電源投入直後の実機でこれらのベクタが何を指しているか（ROM の中の何もしないハンドラか、0 か）は
確かめていない。0000:0000 を残すのは「未設定かどうか」をベクタの値で調べるソフトのためで、未設定のベクタを呼ぶ
ゲストは実機と同じく暴走する。

BIOS ワークエリア（0000:0400–05FF）はホストのものを写し、次を直す。

- ブートデバイス、ディスク装備情報（FDD 2 台、HDD なし。参考実装の起動手順に合わせ、2HD・1.44MB で起動するときは
  1MB インタフェースの 2 台（055Ch = 03h）、2DD・2D のときは 640KB インタフェースの 2 台（055Dh = 30h）として見せ、
  DA/UA はそれぞれ 90h・30h・70h・50h）。この 2 つはドライブ 0 のイメージの種別で決まるので、IPL を読むとき
  （`load_ipl`）に書く。`-fdd0` を付けずに起動したときは、ワークエリアを写す時点ではまだイメージが選ばれていない
- 拡張メモリ量（0）
- 機種判別と装置の有無のフラグ（機種は PC-9801VM、装置の有無はホストの実物に合わせる。値は資料で確かめて決める）
- DIP スイッチ・メモリスイッチから ITF が導く設定（§15）
- キーバッファとシフト状態（空にする）

メモリスイッチは実物のテキスト VRAM の中にあってゲストと共有されるので、ここで設定値を書き込む（§15）。

残りの下位メモリは 0 で埋める（起動時に 640KB 全体を埋めてから、上の内容を置く。XMS で確保した領域には前の内容が
残っているので、埋めないと、前に動いたゲストやホストのプログラムの残りがゲストから見える。リセットでは消さない。§10）。
画面はテキスト消去・グラフィック非表示にしてから IPL に入る。

起動は、仮想ドライブ 0 の先頭セクタを読んで所定の番地に置き、ブートデバイスを設定して飛ぶ。

いまの実装（`vbm98.c`）はこのうち、ベクタ表とワークエリアの写し、INT 1Bh のベクタの差し替え、
装備情報（FDD 2 台、HDD なし）、起動装置、IPL の読み込み、ベクタの規則 1、規則 2（下の「ROM の入口の追跡」）、
規則 3 の簡略版（RAM を指す 00h〜1Fh のベクタのうち入口を突き止められなかったものは、横取り印へ向けて
「IRQ なら EOI を出して戻る」。あわせて、その IRQ をゲストの割り込みマスクの初期値で閉じる（下の「ホストの IRQ」）。
20h〜FFh は下の「20h 以上のベクタ」）、RAM を 0 で埋めること、表示系の初期化
（§16）、メモリスイッチの書き込み（`-memsw`）、DIP スイッチの反映（`-dipsw`。§15）、拡張メモリ量を 0 にすること
（0401h と 0594h の語）、テキスト画面の消去まで。
機種判別のフラグ、キーバッファの消去は未実装。ハードウェア割り込みは、ゲストの
割り込みマスクのままゲストへ届く。マスクの初期値はホストの現在値に、下の「ホストの IRQ」のビットを足したもの。
ホストの現在値は、NP2 系の ITF が電源投入時に書く
7Dh/71h と同じ（確認済み: NP2kai `bios/bios.c` の `bios_itfprepare` を読んだ。実機の ITF も同じ値かは
未検証）。

## 7. ホストサービス呼び出し

ゲストの要求をホスト世界で処理する手順。FDD BIOS もメニューもこの 1 本の経路を通る。

1. モニタが要求ブロック（機能番号、ゲストのレジスタ）を作る。書き込み系なら、ゲストのバッファを転送バッファへ複写する
2. ゲスト側のハードウェア状態を控え、ホスト側の状態に戻す（下表）
3. ホスト世界へ移り、C の受付関数を呼ぶ
4. 戻ったらゲスト側のハードウェア状態を復元する
5. 読み出し系なら転送バッファからゲストのバッファへ複写し、結果のレジスタと BIOS ワークエリアを書いてゲストへ戻る

| 切り替える状態 | FDD BIOS | メニュー |
| --- | --- | --- |
| 割り込みマスク | ○ | ○ |
| A20 | ○ | ○ |
| タイマ（8253 のカウンタ 0） | ○ | ○ |
| テキスト画面の内容と表示状態 | — | ○ |
| キーボードの押下状態の後始末 | — | ○ |

切り替える状態は表として持ち、項目を足せるようにする。画面を触らない FDD BIOS の経路は
短く保つ（アプリのロード中に画面がちらつかない）。

いまの実装は、モニタが `mon_run` から戻ることで世界を切り替え、ゲストのメモリとの複写は
XMS の転送（機能 0Bh）でホスト側から行っている。切り替える状態は割り込みマスクだけ。
タイマは未実装: ホストの BIOS / DOS がホスト世界でカウンタ 0 を設定し直すことがあり（§12。DOSBox-X で確認）、
ゲストが設定した周期割り込みが戻ったあと止まりうる。8253 は設定を読み出せないので、ゲストの 77h / 71h への
書き込みをトラップして写しを持ち、戻るときに書き直す形になる（位相はずれる）。開発用の `-tick` の時計だけは
戻るたびに設定し直している。
転送バッファ（D5）は fdbios と共有している。

切り替えの規則: **ゲストの割り込みマスクが効いている間に、ホストのベクタ表で割り込みを受けては
いけない。** マスクの入れ替えと `mon_run` の出入りは割り込み禁止で行い、ゲスト世界（モニタの IDT）に
入ってから許可する。守らないと、ゲスト宛ての割り込みがホストの既定ハンドラに食われ、ハンドラ側で
再許可する種類の割り込み（CRTV = VSYNC）はそこで途絶える（確認済み: NP21/W でイース2 の VSYNC が
INT 1Bh の処理をまたいだ直後に止まり、禁止を入れると続いた）。

### リアルモードへ戻るときの CPU の状態

ホストがリアルモードのとき、ゲストから戻るたびに、CPU の状態を入る前と同じにする（`monasm.S` の `mon_enter`・
`leave_low`・`rm_back`）。D1 の「何も仮想化せずに動く」は、ホストから見て、CPU がリアルモードを離れなかったのと
同じに見えることが前提になる。16 ビットのソフトが触らない状態は、386 以降向けの常駐物（XMS ドライバ、ディスクの
BIOS など）が呼び出しをまたいで当てにしていることがある。

| 戻すもの | やり方 | `-rmfix` のビット |
| --- | --- | --- |
| PE を落とす手順 | Intel の資料の順にする: セグメントレジスタを入れ、LIDT でリアルモードのベクタ表を指し、PE を落とし、直後の far JMP で CS を入れ直す | 01 |
| FS・GS の値 | 入るときに控えて戻す | 02 |
| DS・ES・FS・GS の限界 | リアルモードでも、限界は CPU の中に残っている値が使われる。入る直前に 64KB を越えているかを調べ（番地 10000h を読んで一般保護例外になるか。`rm_limits`）、越えていたものには 4GB の限界を入れ直す。SS は 64KB | 04 |
| EBX・ECX・EDX・ESI・EDI・EBP と、EFLAGS・ESP の上位 16 ビット | 入るときに控えて戻す | 08 |
| GDTR、CR3 | 入るときに控えて戻す | 10 |

戻せないもの: TR（空に戻す命令がないので、モニタの TSS を指したままになる）、LDTR（0 にする）。
開発用の `-rmfix <16進>` で、戻すものをビットで選べる（既定は 1F = 全部。00 はどれも戻さない）。実機でどれが効くかを
切り分けるためのもの。起動時に、リアルモードから動かすときの状態（限界が 64KB を越えているレジスタ、FS・GS の値、
`rmfix`）を 1 行出す。

EMM の下では VCPI のサーバが仮想86 のタスクへ戻すので、セグメントの限界や GDTR などはサーバのものに戻る。こちらで
戻すのは FS・GS の値と 32 ビットのレジスタの上位だけ。限界は調べない（調べるための例外が EMM に届く）。

確度:

- どれも戻さない（`-rmfix 00`）と、戻るたびに FS・GS が 0 になり、32 ビットのレジスタの上位が変わり、GDTR が
  モニタのものを指したままになる。戻す設定では 3 つとも元のままになる。確認済み（DOSBox-X、NP21/W。モニタ核の
  試験が、印を入れてからゲストを動かして読む）
- セグメントの限界と、PE を落とす手順の違いは、試験で見えない（未検証）。DOSBox-X と NP21/W は、リアルモードで
  限界を越える読み出しを例外にしない（§12）
- 実機で要るかどうか: 386・486 の 2 機種で、どれも戻さない版をリアルモードのホストから起動すると、ゲストから
  戻った直後の DOS のディスク読み込みや XMS の転送で止まる、という報告がある（同じ機種でも EMM の下では動く。
  Pentium の 1 機種ではリアルモードでも動く）。表のどれがその原因かは未確認で、戻す版が実機で動くかも未確認

## 8. FDD BIOS エミュレーション

3 層に分ける。上 2 層がホスト世界の C、いずれもホスト OS 上で単体検証する。

| 層 | 役割 | 状態 |
| --- | --- | --- |
| BIOS 意味論 | INT 1Bh の機能番号ごとの動作。レジスタとステータスの組み立て、READ ID の巡回、複数通りデータの使い回し、特殊読み込み、マルチトラック、64KB 境界、ワークエリアへ書く内容 | 実装・検証済み（`src/core/fdbios.c`。ホスト OS 上 70 項目） |
| ドライブ | 仮想ドライブの管理（器は 4 台ぶん、ゲストに見せるのは 2 台）。媒体種別とデバイス種別の照合、書き込み禁止、ヘッドの位置 | `fdbios.c` の `struct fdb` に含めた。イメージの出し入れは `img[]` の差し替え |
| ディスクイメージ | 4 形式（内部では 5 種）を「トラックごとのセクタ ID 一覧＋データ位置」という 1 つの見え方に揃える | 実装・検証済み（[disk-image-formats.md](disk-image-formats.md)） |

ディスクイメージ層はセクタの ID（C・H・R・N）、密度、DDAM、収録時のステータス、複数通りの
データ、特殊読み込みを区別して持つ。標準的でない構造のディスクを NFD や FDD 形式で扱うには
これらが要る。FDI と RAW は一様な構造として同じ見え方に合成する。

BIOS 意味論の層（`fdb_call`）は、ゲストのレジスタを受け取り、ステータス（AH）と、転送バッファとの間で
動かす長さ、BIOS ワークエリアへ書く内容（装備情報、割り込み待ちの印、動作モード、結果の 8 バイト）を
返す。ゲストのメモリには触れない。読み込み系では呼んだあとに転送バッファの先頭から `xfer` バイトを
ゲストの ES:BP へ、書き込み系では呼ぶ前にゲストの ES:BP から BX バイトを転送バッファへ写す
（`fdb_direction`）。この分担により、意味論はホスト OS 上で全部試験できる。

### INT 1Bh について読み取ってあること

BIOS 意味論の層の根拠。参考実装（NP2kai `bios/bios1b.c`）と、その挙動を踏襲した別実装
PC98_Open_BIOS（0BSD、`src/int1b.asm` と `tests/test_fdd_bios.py`）から読み取った。
どちらもエミュレータや互換 BIOS であって実機の ROM ではない。両者は一致しているが、
実機の資料で裏を取ったものではない。

| 項目 | 読み取った内容 |
| --- | --- |
| AH の修飾ビット | 10h = 先にシーク、20h = 削除データを飛ばす、40h = MFM、80h = マルチトラック |
| デバイス種別（AL 上位ニブル） | 9 = 1MB インタフェースの 2HD、3・B = 1.44MB モード、1 = 1MB インタフェースで 2DD 媒体、7 = 640KB インタフェースの 2DD、F = 640KB インタフェースで 2HD 媒体、5 = 640KB インタフェースの 2D（倍ステップ） |
| ステータス | 00 正常、10 書き込み禁止（センス）、20 DMA 境界、30 トラック終端を越えた、40 装置なし、50 オーバーラン、60 準備できていない、70 書き込み禁止、A0 ID の CRC、B0 データの CRC、C0 該当セクタなし、D0 シリンダ違い、E0 アドレスマークなし |
| 結果の格納 | 0564h + ユニット × 8 に ST0 ST1 ST2 C H R N NCN。R は FDC の結果と同じく「次のセクタ」 |
| AL のビット 2 | 物理ヘッドを DH から反転する（`hd = (DH xor (AL >> 2)) and 1`）。ID の照合は DH のまま |

本実装で決めたこと（資料に無い、または資料どうしで違うところ）:

- 収録ステータスが 20h 以上のセクタは、データを渡したうえでそのステータスで打ち切る（参考実装は最後のセクタの値を返すだけ）
- 複数通りのデータを持つセクタは、読むたびに次の通りを返す
- 特殊読み込みの項があれば、同じ命令・同じ ID のセクタより優先する（NFD r1 の資料のとおり）
- ID の照合は、C・H・R・N が全部合う ID を先に採る。無ければ、H・R・N が合って C だけ違う ID を採る。FDC はここで
  D0h（シリンダ違い）を返すが、エミュレータ上で吸い出したイメージには ID の C が実物と違うものがあり
  （disk-image-formats.md の「解釈が分かれる点」）、それを読めるようにするために緩めている（参考実装は R しか見ない）。
  R の合う ID が C も H か N も違うものだけなら D0h、H か N だけ違うなら C0h。C を除いて採ったセクタの数は数えて
  おき、起動時（IPL のセクタがそうだったとき）と終了時に表示する。前提と限界: 「シークせずに別のシリンダ番号で読むと
  D0h になる」ことを当てにしたゲストは、ヘッドの位置のセクタが読めてしまう。該当するゲストは未確認
- トラック終端を越えて MT なしなら 30h
- READ ID は MFM 指定（AH ビット 6）がなければ E0h（参考実装と同じ）
- フォーマットは一様な形式（RAW・FDI）だけ。他の形式は D0h
- 09h・0Ch（削除データの書き込み・読み込み）は 05h・06h と同じ扱い。未対応の機能番号は 60h（参考実装と同じ）
- 動作モード（0493h・05CAh）の初期値は 33h（資料なし）

以下は参考実装だけから読み取った、より細かい事項。

| 項目 | 読み取った内容 |
| --- | --- |
| 入力 | AH = 機能（下位 4 ビット）と修飾ビット、AL = デバイス種別（上位ニブル）とユニット番号（下位 2 ビット）、BX = 転送バイト数、CL = シリンダ、DH = ヘッド、DL = セクタ、CH = セクタ長 N、ES:BP = バッファ |

| 修飾ビット | 10h = 先にシークする。80h = マルチトラック（ヘッド 0 のトラック終端を越えたらヘッド 1 へ続ける） |
| 戻り値 | AH = ステータス。20h 以上なら、スタックに積まれた FLAGS の CF を立てて戻る |
| 準備できていない | 60h |
| センス | 正常で 00h、書き込み禁止で 10h。AL のビット 7 が立つ種別では 01h を足す。立たない種別では、動作モードの領域（0000:0493 または 0000:05CA）のユニットごとのビットに応じて 01h・04h を足す。`(AX and 8F40h) = 8400h` の呼び出しでは 08h（1MB / 640KB 両用ドライブ）を足し、さらに AH のビット 6 が立っていて 1.44MB 対応なら 04h を足す |
| 読み込み・ベリファイの失敗 | 該当セクタなしなどで C0h、シークの失敗で E0h、形式のパラメータが引けないとき D0h |
| 初期化以外の全機能 | FDC の割り込みが割り込みコントローラでマスクされていると 40h |
| イメージが持つステータス | NFD のセクタ ID にある収録時の結果（byStatus）を、そのまま AH として返している |
| 結果の格納先 | 0000:0564 + ユニット番号 × 8 に、ST0・ST1・ST2・C・H・R・N・シリンダ番号の 8 バイト。ただしこの並びは参考実装の中で無効化されているコード片から読んだもので、有効な経路の書き込み内容は未読 |
| 割り込み待ちの印 | 完了時に 0000:055E（1MB 系）または 0000:055F（640KB 系）の、ユニットに対応するビットを落とす |

| IPL の起動 | [§12](#12-確度と検証計画) の表を参照 |

## 9. ホットキーとディスク交換

ホットキーは [spec.md](spec.md) の 6 つ（CTRL + GRPH + HELP / テンキーの 0 / テンキーの 1 / COPY / DEL / STOP）。
DEL は実機のリセットと同じ組み合わせなのでリセットに充て、メニューは HELP に置いた（利用者が NP21/W で確認）。

- キーの検出: キーボードの割り込み（IRQ1）はモニタが先に受ける（IDT は全ベクタがモニタのもの）。
  モニタがデータポートを読んで記録し、CTRL と GRPH の押下状態を追う。ホットキーでなければ割り込みを
  ゲストへ反射し、ゲストがデータポートを読むのをトラップして記録した値を返す（ステータスポートも、
  記録した値が未読のあいだは「受信あり」を返す）。ホットキーなら反射せず、モニタが割り込み
  コントローラに EOI を送って、ゲストには何も届けない
- ホットキーを拾ったら、CTRL・GRPH・そのキーが全部離されるまでモニタの中で待ち、離した符号を読み捨ててから
  ホストへ移る（`kbd_wait_release`）。待たずに移ると、押した符号はゲストに、離した符号だけがホストに届く。
  ホストの BIOS によっては、押していないキーが離されるとシフト状態が反転したままになる（実機の報告:
  PC-9801RA2 で、戻ったあと CTRL と GRPH を押しながらでないと普通に入力できなかった。PC-9821Cr13 では
  起きない）。待つ間は割り込み禁止のままなので、キーボードの受信はポーリングで読む。押し続けられても
  固まらないよう、VSYNC を約 3 秒ぶん数えたら打ち切る。エミュレータの試験では実物のキー入力を通せないので、
  この待ちは自動試験で通っていない（未検証。実機の結果待ち）
- メニューへ移る時機: 検出した時点でゲストが割り込み処理の途中だと、そのままホストへ移ると
  ホスト側に割り込みが届かない。割り込みコントローラに処理中の割り込みが残っていない時点まで
  待ってから切り替える（未実装。下の「やっていないこと」）
- DOS に戻るとき（終了、例外での停止）は、割り込みコントローラに処理中の割り込みが残っていれば、EOI を出して
  片付ける（`pic_settle`）。ゲストはもう続きを実行しないので、片付けてよい。残したままだと、それ以下の優先順位の
  割り込みがホストに届かない。スレーブ側の割り込みの処理中なら、スレーブ側の全部（ディスクの割り込みを含む）が
  止まる。片付けたときは `interrupts were in service when the guest was left` の行を出す。メニューを開くときは
  片付けられない（ゲストがあとで続きを実行する）ので、残っていたことをログに書くだけにしている
- 画面: メニューはテキスト画面だけで描く。テキスト VRAM の表示範囲と、テキスト表示の状態
  （表示の有無、カーソル、スクロール設定、桁数・行数のモード）を退避し、閉じるときに戻す。
  グラフィック表示はメニューのあいだ GDC のコマンド（BCTRL の STOP）で消し、閉じるときにゲストの状態
  （ゲストがグラフィック GDC のコマンドポート A2h に書いた START / STOP / SYNC を追って持つ）が ON なら
  START を出す。VRAM とパレットには触らない
- 再開時: メニュー中に離されたキー（CTRL・GRPH を含む）をゲストは見ていないので、押しっぱなしに
  見えないよう、離されたキーの break コードを割り込みの反射の仕組みで 1 つずつゲストへ届ける
- VM メニュー（CTRL + GRPH + HELP）の項目: ドライブ 0 の取り出し・入れ替え、ドライブ 1 の取り出し・入れ替え、
  スクリーンショット（§17）、終了、リセット（§10）。各項目は対応するホットキーで直接も呼べる。終了とリセットは
  メニューでは問い合わせの後、ホットキーでは終了だけ問い合わせる（リセットは実機の組み合わせどおり即時）
- 取り出し・入れ替え: ファイル選択に「取り出すだけ（空にする）」の選択肢を含める。
  選択はホスト世界の C で、MS-DOS のファイル検索を使って作る
- 終了（CTRL + GRPH + STOP）: 問い合わせに応じたときだけ §10 の終了処理へ進む。そうでなければ再開する

いまの実装（`vbm_r0.c` の `kbd_irq`、`vbm98.c`、`menu.c`、`ui.c`）: 6 つのホットキーを検出する。HELP でメニュー
（ディスク交換 2 つ、スクリーンショット、終了、リセット）、テンキーの 0/1 でそのドライブのファイル選択、COPY で
スクリーンショット（§17）、DEL でリセット（§10）、STOP で終了の問い合わせ。ゲストが割り込み禁止で HLT したときもメニューを開く
（spec.md の「アプリの停止」）。`-fdd0` がなければ起動前にファイル選択を開く。画面はテキスト画面の見えている
範囲を退避・復元し、文言は Shift-JIS でテキスト VRAM に直接描く（`ui_text.txt` → ビルド時に `ui_text.h`。
コードの並びは §12）。キーはホストの BIOS（INT 18h AH=00h/01h）で読む。再開時は CTRL と GRPH の break コード
を、ゲストのキーボード割り込みハンドラを IRET の戻り先を横取り印（HOOK_KBD）にして呼ぶ形で届ける（押された
ままに見えないように。離されたキーは追っていないので常に 2 つ）。ファイル選択は MS-DOS のファイル検索で一覧を
作り（イメージの拡張子で絞り、TAB で全ファイル）、サブディレクトリへはカレントディレクトリを移して入る。
確認済み（NP21/W）: ソーサリアンの実行中に開いて ESC で戻ると続きが動く。試験は `run_dos_tests.py menu`。
グラフィック表示は `ui_open` で BCTRL の STOP（A2h ← 0Ch）、`ui_close` でゲストの状態が ON なら BCTRL の START
（A2h ← 0Dh）を出す（`vbm98.c` の `vm_gdisp_pause` / `vm_gdisp_resume`。コマンドの前に状態ポート A0h の FIFO full が
下りるのを待つ）。ゲストの状態は A2h への書き込みをトラップして追う（`vbm_r0.c` の `vid_gdisp`。START / BCTRL の
START / SYNC の表示 ON で 1、STOP / SYNC の表示 OFF で 0。起動時の初期化 §16 で 0）。ゲストがコマンドの引数を
書いている途中でメニューが開くと、挟んだコマンドで引数の列が切れる（ホットキーはキーボード割り込みで来るので
時機は選べない）。テキスト表示はメニューが INT 18h AH=0Ch で ON にするので、ゲストが消していた（テキスト GDC の
コマンドポート 62h を同じ要領で追う `vid_tdisp` が 0）なら、閉じるときに 62h へ STOP を出して消し直す。
モードフリップフロップ（68h）の KAC（コードアクセス）モードが ON だと、テキスト画面の 2 バイトの文字が 1 バイトの
文字として描かれ、メニューの漢字が読めない（実機の報告: PC-9821Ap2 で、あるゲームを CTRL + GRPH + STOP で終了
しようとしたときの確認の行。§12）。68h への書き込みをトラップして項目ごとの写しを持ち（`vid_mode68`。起動時の
初期化 §16 で BIOS が設定する値を入れる）、ON なら `ui_open` で OFF（68h ← 0Ah）にし、`ui_close` で ON（0Bh）に戻す。
ログにその旨を残す。試験は `menu` に、KAC を ON にしたまま待つ IPL の 1 本（ログの行で見る。描かれ方は自動試験では
見えないので、NP21/W の窓を手作業で撮って確かめた）。
やっていないこと: 20 行・40 桁モード、テキストの表示開始番地、メニューを開くときに処理中の割り込み（ISR）が残っている時機の回避、
音源の消音（ゲストが止まるので、鳴っていた音はメニューのあいだ鳴り続ける。spec.md）。開発用に `-stopkey` / `-shotkey <スキャンコード>`（STOP / COPY の代わりのキー）、
`-menuat`（刻みで開く）、`-menukeys`（キー入力の代わりの列）がある。

## 10. リセットと終了

- ゲストが CPU リセットをかけた（リセットベクタ FFFF0h への飛び込み。横取り印 HOOK_RESET）、ホットキー
  CTRL + GRPH + DEL、VM メニューのリセット: 仮想マシンを §6 の初期状態に作り直し、仮想ドライブの中身は
  入れたままで IPL からやり直す。いまの実装（`vbm98.c` の `vm_reset`）が戻すもの: 表示系（§16。ホストの表示状態
  の控えは最初の 1 回だけ取り、リセットでは取り直さない）、メモリスイッチのページの写し（実物から取り直して
  `-memsw` を書く）、ベクタ表と BIOS ワークエリア（ホストから写し直して §6 の直しを再適用。横取り印の登録は
  番地が同じなので最初の 1 回だけ）、テキスト画面の消去、キーボードの写しと break コードの注入の待ち行列、
  割り込みマスク（起動時の値）、IPL の読み直し。ゲストの RAM の残りは消さない（実機のリセットでも RAM は残る。
  試験の IPL はこれを使って 1 回目と 2 回目を見分ける）。ドライブ 0 が空ならファイル選択を開き、取り消したら
  終了する。やっていないこと: リセット用ポート（F0h）への書き込みの検出、CTRL と GRPH が押されたままの状態の
  引き継ぎ（離されたときの break コードはそのままゲストに届くので、押しっぱなしには見えない）。
  確認済み（NP21/W）: `run_dos_tests.py boot` で、IPL が FFFF:0000 へ飛んで起こすリセットと、メニューの項目からの
  リセットの後に IPL が読み直され、RAM に置いた印が残り、INT 1Bh の往復が再び通る。ホットキー DEL の経路は同じ
  `vm_reset` を呼ぶが、試験環境ではそのキーを送れず未確認
- メニューから終了: ホスト世界へ移ったあと、ゲストが変えたハードウェアを MS-DOS が使える状態に
  戻す（割り込みマスク、タイマ、テキスト画面の再初期化、グラフィック非表示、音源の消音など。
  項目は表として持つ）。メモリとファイルを解放してプロンプトへ戻る

メモリモデル（[spec.md](spec.md) 2026-10-10）: gcc-ia16 の small（コード 1 セグメント、データ 1 セグメント、各 64KB）。
gcc-ia16 にあるのは tiny・small・medium だけで、compact と large は無い。medium にはしない: 全関数が far になり、C から
呼ぶアセンブリの関数の引数の位置と戻り方が変わるうえ、ring 0 の C はファイルをまたぐ呼び出しがリアルモードのセグメント値を
使う far call になって保護モードで動かない。コードが収まらなくなったら、ホスト側だけで動く関数に `__far` と
`__attribute__((far_section))` を付けて別のコードセグメントへ出す。出せないのは、ring 0 で動く関数、アセンブリから near で
呼ぶ関数、関数ポインタで渡す関数。本体に適用済み（`menu.c`・`ui.c`・`shot.c`・`png.c` の全関数と、`vbm98.c` の
ホスト側だけで動く関数。INT 1Bh の往復で毎回通る関数は、far call の分だけ遅くなるので near のまま）。確認済み
（DOSBox-X、NP21/W で全試験が通る）。実機では未確認。データ側は、まとめて書いてまとめて読み戻す置き場を XMS へ出す（§3）。スタックはデータセグメントの
.bss の上に載るので、`tools/build16.sh` がスタックに残る量も見る。

`src/core/` は int が 16 ビットの環境でも動くように書く（位置や大きさの計算は 32 ビット型で明示する）。

## 12. 確度と検証計画

## 13. 未決の設計判断

提案と、後から変えるときの値段。決まったら [spec.md](spec.md) の確定事項へ移す。

| 項目 | 提案 | 理由 | 後から変える値段 |
| --- | --- | --- | --- |
| 例外とソフトウェア割り込みの見分け方 | ベクタ 0 と 6 のゲートだけ DPL=0 にする（§14） | 例外と INT 命令が同じベクタに届き、処理が違う。命令の並びから推し量る方法もあるが、確実でない | 小。ゲートの属性 2 つと、一般保護例外の分岐 1 つ |
| EMM の下でのホスト世界の割り込みの取りこぼし | §18 の「やっていないこと」。ホスト世界の滞在を短くするか、EMM 側に割り込みを渡さない手段を探す | こちらの CLI が仮想になるので、§7 の手が効かない | 中。対策が §7 の切替の手順に波及する |

### GDC の違いの吸収（μPD7220 と μPD72020）

利用者の問い（2026-10-11）: ホストの GDC が μPD72020 のとき、ゲストに μPD7220（PC-9801VM）を見せて、違う振る舞いを
トラップで上書きできるか。調べた範囲（§12 の「GDC の種類」）での答え:

| 違い | ソフトウェアで吸収できるか |
| --- | --- |
| グラフィックのスクロール分割が 4 つ（7220）と 2 つ（72020） | できない。分割はディスプレイへの描画を GDC が走査中に行うもので、CPU は関与しない。ポート A0h の SCROLL コマンドのパラメータはトラップで読めるが、3・4 番目の分割を 72020 に描かせる手段がない。VRAM の内容を写し替えて同じ見え方を作る手は、毎フレーム数十 KB の転送になり、ゲストを止めて行う VBM98 の作りでは成り立たない |
| KAC モードのときの描き方 | できない（同じく描画の違い）。ゲストが KAC を ON にして 1 バイト文字の描画を期待するソフトがあれば、72020 のホストでは違って見える。該当するソフトは知られていない |
| クロック（2.5MHz / 5MHz）と描画の速さ | 一部できる。クロックは 6Ah への 82h / 83h で切り替わる（参考実装。§12）ので、ゲストの間だけ 2.5MHz にする手はある。いまは SW2-8 を OFF に見せることでゲストの BIOS に 2.5MHz を選ばせている（§15）。ただし同じクロックでも 72020 のほうが速いことがありうる（描画の完了をステータスの DRAW ビットで待たずに時間で待つソフト）。これは吸収できない |
| コマンドやステータスの細かな違い | 不明。参考実装は FIFO とステータスを種類で分けていないので、分けるべき違いが知られていない。あるとすれば、A0h / A2h のトラップで読み替えることになるが、描画のパラメータは頻繁に書かれるので、常時トラップすると遅い（§17 の CSRFORM の扱いと同じ事情） |

結論: 違いの大半は描画そのものにあり、CPU 側のトラップでは上書きできない。やらない。DIP SW の読み替え（SW2-8）と、
必要なら 6Ah でのクロックの切り替え（未実装）までが、こちらで持てる範囲。

## 14. V30 エミュレーション

ゲストに見せる CPU は V30（[spec.md](spec.md)）。ホストは 386 以上なので、V30 にあって 386 にない
命令をモニタが代行し、386 にあって V30 にない振る舞いの一部を V30 に合わせる。CPU を解釈実行する
のではなく、該当する命令が例外になったときだけ介入する（D10）。したがって、例外にならない差は直せない。

オペコードと意味は MAME の NEC コア（BSD-3-Clause。`src/devices/cpu/nec/necinstr.hxx`・`necmacro.h`）を参考実装として
読んで確かめた（§12。コードは写していない）。386 以降での届き方は、下の表と §12 の試験の記録による。

いまの実装（`src/mon/v30_r0.c` の `mon_v30_emulate`、`vbm_r0.c` の `mon_on_fault`、試験は `tests/monprobe` の
`g_v30_*`）: `-v30 on` のとき、未定義命令例外（ベクタ 6）とエラーコード 0 の一般保護例外で CS:IP を読み直し、
0Fh から始まる V30 の命令（下の表のうち BRKEM 以外）を実行して IP を進める。セグメントの上書きのプリフィクスに
従い、16 ビットのアドレスだけ扱う（66h / 67h が付いていれば代行しない）。代行できないゼロ除算と未定義命令は、
ゲストがそのベクタに自前のハンドラを持っていれば INT 0 / INT 6 として反射し（ゼロ除算は `-v30 on` で IP を命令の
後ろへ進める。長さは DIV / IDIV の ModRM と AAM から読む）、持っていなければ止めて報告する。CR4（RDTSC を
例外にする TSD）はまだ触っていないので、Pentium 以降のホストでは 0F 31（INS reg,reg）が RDTSC として実行される
（代行そのものは、0F 31 が例外になる設定の DOSBox-X で確かめてある。§12）。

### 代行する命令

V30 固有の命令は 0Fh で始まる。386 ではこの並びが別の命令（特権命令または未定義命令）に当たるので、
一般保護例外か未定義命令例外としてモニタに届く。モニタは CS:IP から命令を読み直して代行し、
IP を進めてゲストへ戻る。

| V30 の命令 | バイト列 | 386 での扱い（届き方） |
| --- | --- | --- |
| TEST1 / CLR1 / SET1 / NOT1（ビット操作。回数は CL または即値） | 0F 10〜1F | 未定義命令例外。ただし Pentium Pro 以降では 0F 18〜1F が無動作命令として実行され、届かない |
| ADD4S / SUB4S / CMP4S（パック BCD 文字列の加減算・比較） | 0F 20 / 22 / 26 | 制御レジスタの転送（特権命令）と解釈され、一般保護例外 |
| ROL4 / ROR4（ニブルの回転） | 0F 28 / 2A | 未定義命令例外。SSE を持つ CPU では CR4 の OSFXSR を 0 にしておけば未定義命令例外になる |
| INS / EXT（ビットフィールドの挿入・抽出） | 0F 31 / 33 / 39 / 3B | 386 では未定義命令例外。Pentium 以降では 0F 31 が RDTSC として実行されるので、CR4 の TSD を立てて一般保護例外にする。0F 33 は RDPMC で、既定で一般保護例外 |
| BRKEM（8080 エミュレーションモードへ） | 0F FF | 未定義命令例外。代行せず、ゲストを止めて報告する |

### 合わせる振る舞い

| 差 | 対応 |
| --- | --- |
| ゼロ除算例外の戻り番地: 8086/V30 は次の命令、286 以降は当該命令 | `-v30 on` ではベクタ 0 の反射時に IP を命令の後ろへ進める。命令長は CS:IP から読み解く（`mon_v30_div_len`）。ゲストがベクタ 0 に自前のハンドラを持たないときは止めて報告する（反射すると横取り印へ戻って同じ命令を繰り返すため） |
| 未定義命令: V30 は INT 6 を発生する | 代行できない命令はゲストの INT 6 へ反射する（386 の未定義命令例外も同じ経路）。ハンドラがなければ止めて報告する |

### 直せない差

| 差 | 理由 |
| --- | --- |
| REPC / REPNC プリフィクス（64h / 65h） | 386 では FS / GS のセグメントオーバーライドとして例外なく実行される |
| FPO2（66h / 67h） | 386 ではオペランドサイズ / アドレスサイズのプリフィクス |
| シフト回数のマスク（286 以降は下位 5 ビットに切る） | 例外にならない。V30 が切らないかどうか自体も未確認 |
| PUSH SP が積む値 | 例外にならない |
| 8080 エミュレーションモード | 別の CPU の解釈実行になる。対象外 |
| 386 以降にしかない命令をゲストが実行した場合 | そのまま実行される。V30 で動かないという事実は再現しない |
| 実行速度 | spec でサイクル正確性は担保しない |

ホストの CPU の世代で、届く命令の範囲が変わる（上の表）。起動時に世代を見分け（EFLAGS の AC / ID
ビット、CPUID）、CR4 を設定できるものは設定し、残りは「この CPU では代行できない命令」として表示する。
NP21/W では SSE の命令が CR4 に関係なく実行されるので、0F 10〜1F・28・2A の代行は効かない（§12）。

### 例外とソフトウェア割り込みの見分け

ベクタ 6（未定義命令）と 0（ゼロ除算）は、ゲストの `INT 6` / `INT 0` 命令でも同じベクタに届く。
例外なら代行や IP の補正をし、命令なら反射するだけ、と処理が分かれるので見分けが要る。
提案: この 2 つだけゲートを DPL=0 にする。仮想86モードからの `INT n` は DPL が足りず一般保護例外になり、
エラーコード（ベクタ×8+2）でどのベクタかが分かるので、モニタが IP を命令の後ろへ進めて反射する。
例外は直接そのベクタへ届く。この 2 つは IRQ のベクタ（08h〜17h）と重ならない。確度は §12。

### 実装の置き場所と検証

ring 0 で動く C（`src/mon/v30_r0.c`）。命令の読み解きとオペランドの読み書きは `mon_peek` / `mon_poke` で行う。
検証は `tests/monprobe`: V30 固有の命令を既知の値で実行する断片（`guest.S` の `g_v30_*`）を走らせ、報告された
レジスタとメモリの値を表の期待値と比べる。例外にならずに実行された断片（そのホストでは SSE や RDTSC に当たる）は
「この CPU では見ない」と報告して飛ばす。届き方の記録は §12。

## 15. スイッチの反映

### DIP スイッチ

実機では I/O ポートで読める（ポートとビットの割り当ては §12: 参考実装から）。`-dipsw` があるときは、
ゲストがそのポート（31h・33h・42h）を読むのをトラップし、設定された値から作った値を返す（`vbm_r0.c` の
`dip_port`）。なければ、31h だけをトラップして bit 7（SW2-8）を 1（OFF）にして返し、33h・42h はホストの値が
そのまま見える（下の「省略時」）。31h は SW2 の 8 ビットそのもの、33h は bit 3
だけが SW1-1、42h は bit 4・3・1 だけが SW1-3・SW1-8・SW3-8 で、それ以外のビット（RS-232C の状態、カレンダ
時計、クロック系の印）は実機の値を残す。16 ビット幅の IN（30h から 2 バイト、など）は差し替えない。

ITF が DIP スイッチから導いて BIOS ワークエリアに書く値も、`-dipsw` のときはホストの写しの上でゲストの値から
作り直す（`vbm98.c` の `dipsw_workarea`。式は参考実装 `bios_reinitbyswitch` から。§12）: 054Ch の bit 6（SW1-1
ON）と bit 0（SW1-8 ON）、054Dh の bit 5（SW2-8 ON）、0501h の bit 6（SW3-8 OFF = V30）、0480h の CPU 種別
（SW3-8 が OFF なら 00h = V30。ON ならホストの値のまま）。桁数・行数は §16 の表示系の初期化で INT 18h AH=0Ah
に渡す（SW2-3 が OFF なら 20 行、SW2-4 が OFF なら 40 桁）ので、ホストの BIOS がハードウェアも設定する。

省略時（`-dipsw` なし）: SW2-8 だけ OFF に見せる。SW2-8 はグラフィック GDC のクロックで、ON なら 5MHz を使える設定、
OFF なら 2.5MHz だけ（§12）。ゲストは PC-9801VM 相当で、VM の GDC は 2.5MHz だけなので、それに合わせる。変えるのは
ゲストが 31h から読む値の bit 7 と、ゲストのワークエリア 054Dh の bit 5 の 2 つだけで、ほかのスイッチから導く値と
表示系の初期化（§16）は、ホストの値のまま（スイッチとワークエリアの対応は参考実装から読んだもので、実機で確かめた
のは 1 機種だけなので、省略時に触る範囲を広げない）。クロックそのものは、ゲストの中で動く ROM の BIOS がモード設定の
ときにゲストのワークエリアを見て決めるので、ホストのスイッチにも実物のワークエリアにも触らない。終了後は、ホストの
BIOS が自分のワークエリアを見て切り替え直す。`-dipsw ******` と書けば、全部のスイッチがホストの値どおりになる。
確認済み（実機 PC-9821Cr13、SW2 = 73h。利用者の報告）: `-dipsw **F***` で 2.5MHz 前提のゲームの表示が直り、ホストへ
戻ると 5MHz に戻っていた。省略時にこの扱いにした版での実機の結果はまだない。確認済み（NP21/W）: 省略時にゲストが
31h から F3h を読み、054Dh の bit 5 が 0 になる。`-dipsw ******` では 73h と bit 5 = 1（`run_dos_tests.py hook`・`boot2dd`）。
前提と限界: 5MHz を前提にしたソフトは、省略時には正しく表示されないことがありうる（該当するソフトは未確認）。

やっていないこと: ハードウェアの初期化に関わる他のスイッチの意味（SW1-1 の 15/24kHz と SW1-8 の GDC 同期、
SW1-3 のプラズマディスプレイ、など）。ゲストがポートから読む値と、上のワークエリアの値だけを揃える。
起動時にホストのポート 31h・33h・42h の値を表示するので、`-dipsw` の値を組むときの元にできる（SW2 以外は
一部のビットしか読めない）。

確認済み（NP21/W）: `run_dos_tests.py boot` で、ホストの値（31h = 73h、33h = E8h、42h = 94h。SW1-1 ON、SW1-3 OFF、
SW1-8 ON、SW3-8 ON、80 桁 25 行）と見ているビット全部で違う `-dipsw C1F4FB` を渡し、ゲストが読む 3 ポートと
ワークエリアの 5 バイト（0480h・0501h・053Ch・054Ch・054Dh）が設定値どおりになった（8 項目）。実機では未確認。

### メモリスイッチ

テキスト VRAM の属性面の末尾 A3FE0h〜A3FFFh にあり（BIOS が使う 8 個は A3FE2h から 4 バイトおき。§12）。
**`-memsw` も `-dipsw` もホストのスイッチには触らず、ゲストにだけ作用させる**（[spec.md](spec.md)）。実機の
メモリスイッチは電池で保持され、DIP SW2-5 が ON のあいだはライトプロテクトされていて書けない（書き換える
ときは SW2-5 を OFF にしてから行う。§12）。そこで、ゲストにはこのページ（A3000h〜A3FFFh。80 桁 × 25 行の
属性は A2F9Fh までなので表示には使われない）をゲスト専用の写しに差し替えて見せ（`setup_guest`）、`-memsw`
があればその 8 バイトを写しに書く（`memsw_guest`）。ゲストが書き換えた値は、ゲストの中だけで意味を持つ
ものとして終了時に写しごと捨てる。実物の領域を消したり詰めたりしてはいけない（§6 の画面消去は見えている
範囲だけ）。20 行モードやテキストの表示開始番地の変更で A3000h 以降の属性が表示に使われるゲストでは、その
部分の属性だけ実物（ホストの残り物）が見える。ITF がメモリスイッチから導く設定のうち、ゲストの起動に関わる
ものは §6 で行う（未実装）。確認済み（NP21/W）: `-memsw` で SW4 の bit 3 を立てるとゲストからその値が読め、
ソーサリアンが FM 音源のドライバを選ぶ（§12）。

### 値の表記

`-dipsw` の各バイトは、NP21/W の設定ファイル（DIPswtch）と同じ値が同じ意味になるようにする（[spec.md](spec.md)）。
並びと極性は NP2 の実装から: bit n−1 が SW n で、1 = OFF（§12）。ポート 31h が SW2 をそのまま返すので、
`-dipsw` の 2 バイト目はゲストが 31h から読む値でもある。実機のスイッチとポートの極性が同じかは未確認。

`*` の桁（`src/core/optval.c` の `optval_hexmask` が、値 0 とニブル単位の印に分けて読む）は、ホストの同じ桁を
映す（`optval_merge`）。メモリスイッチのホストの値は実物の A3FE2h〜から読む。DIP スイッチのホストの値は
ポート 31h・33h・42h から組み直す（`vbm98.c` の `host_dipsw`）ので、SW2 は全部、SW1 は 1・3・8、SW3 は 8 だけが
映り、読めないビットは 0（ON）になる。ゲストが読める値とワークエリアに導く値は読めるビットだけで決まるので、
読めないビットの穴は見えない。確認済み（NP21/W）: 起動試験で `-dipsw 0*F4FB` の SW1 がホストの値（SW1-3 OFF）に
なり、`-memsw ******08********` で SW4 以外がホストの値になった（同じ出力に表示したホストの値と突き合わせた）。

### I/O ポートの読み替え（-iotrap）

ゲストが指すポート番号をホストの番号に読み替える表（64 個まで。`vbm.h` の `iotrap_guest` / `iotrap_host`。
ring 0 側が持つ）。ゲスト側の番号をトラップし、`mon_on_in` / `mon_on_out` の先頭で読み替えてから、あとの処理
（DIP スイッチの差し替え、キーボードの写し、表示系の写し）を読み替えた先の番号で行う。16 ビット幅の I/O は
読み替えた先の番号 + 1 を上位バイトにする。記録（`-traceio`）にはゲストが指した番号を残す。一覧（`a=b,...`）と
定義ファイル（1 行 `a b`）の読み取りは `optval.c`（ホスト OS 上の試験 `tests/optval`）。値に `=` を含めば一覧、
含まなければファイル名。読み替え先が同じホストのポートを複数のゲストのポートから指してもよい。
確認済み（NP21/W）: 定義ファイル `F31 31` を渡した起動試験で、ゲストが 0F31h を読むと 31h の（DIP スイッチを
差し替えた後の）値が返った。一覧と行の読み取りの書式はホスト OS 上の試験（`tests/optval`）。

### サウンド BIOS（-sbrom）

ROM イメージ（16KB が普通。32KB まで）をファイルから読み、4KB のページに写して、ゲスト向けの写像で C8000h か
CC000h（省略時）からの範囲をそのページに差し替える（`vbm98.c` の `sbrom_setup`。§3 の写像の差し替えと同じ仕組み）。
ホストの同じ番地にある実物（サウンドボードの ROM、または何もない）は、そのぶんだけゲストから見えなくなる。
ゲストが ROM の範囲に書いても写しが変わるだけで、ホストには届かない。やっていないこと: サウンド BIOS の割り込み
（INT D2h）の登録。実機では IPL か N88-BASIC が ROM のヘッダ（CC000h + 2E00h）を見て登録するらしいが、手順は
未確認（§12）。ROM を見せれば足りるアプリが対象で、登録が要るアプリが出たら、ヘッダの読み方を確かめて足す。
確認済み（NP21/W）: 起動試験で、16KB のパターンのファイルが CC00:0000・0001・2000・3FFF で読めた。

## 16. 表示系の初期化と復元

ゲストには「電源投入直後」の表示系を見せる。ホストの MS-DOS は 400 ライン・16 色などの状態を残して
いて、200 ライン前提のベアメタルアプリ（イース1・2）はそのままだと縦に潰れた表示になる（§12）。

起動時（`video_guest`）。ホストの BIOS に設定させるので、あとで写す BIOS ワークエリアも同じ状態になる。
BIOS ワークエリアを写す前に行う。

| 項目 | 電源投入時の値 | 設定の仕方 |
| --- | --- | --- |
| グラフィック表示 | OFF | INT 18h AH=41h |
| グラフィックのモード | 640×200（上）、カラー、ページ 0 | INT 18h AH=42h CH=80h |
| CRT モード | 04h（簡易グラフィック属性）+ SW2-3 が OFF なら 20 行 + SW2-4 が OFF なら 40 桁 | INT 18h AH=0Ah。`-dipsw` があればその SW2 から（§15）、なければホストの現在値の下位 2 ビット（ホストの BIOS が起動時に同じ式で決めた値）をそのまま使う |
| テキスト表示 | ON、カーソルなし | INT 18h AH=0Ch、AH=12h |
| 色数 | 8 色（VM にアナログ 16 色はない） | 6Ah ← 00h |
| GRCG | OFF | 7Ch ← 00h |
| デジタルパレット | 恒等 | A8h ← 37h、AAh ← 15h、ACh ← 26h、AEh ← 04h（ポートと番号の対応は §12） |
| アナログパレット（16 色モード用） | 0〜7 が半輝度の 8 色、8 が灰色、9〜15 が全輝度の 8 色（NP2 の ITF の値。§12） | 6Ah ← 01h で 16 色モードにして A8h（番号）・AAh（G）・ACh（R）・AEh（B）に書き、6Ah ← 00h で戻す。VM にはない機能なので、なければ何も起きない |
| テキスト VRAM | 見えている 4000 バイトを空白・属性 E1h に | 直接書く。属性面の末尾はメモリスイッチなので触らない（§15） |

終了時（`video_host`）は、起動時に控えた BIOS ワークエリアの 3 バイト（053Ch CRT モード、054Ch bit 7
グラフィック表示中、054Dh bit 2 400 ライン）から INT 18h AH=0Ah / 42h / 40h・41h を呼び、テキスト表示を
ON、カーソルを ON にし、テキスト VRAM は両面とも 8KB を丸ごと戻す。グラフィックチャージャーは止める
（7Ch ← 00h）: ゲストが描画の途中で離れると有効なまま残り、そのままだと、チャージャーを使わないソフトが VRAM を
読み書きしてもプレーンの中身に届かない。16 色モードとパレットはホスト側の
値を読み出せないので戻さない（MS-DOS のテキスト画面には影響しない）。

やっていないこと: EGC の状態、GDC の表示開始番地（テキストのハードウェアスクロール）、31kHz の
ホストを 24kHz にすること、グラフィック VRAM の消去（実機のリセットでも残る）。

## 17. スクリーンショット

ホットキー CTRL + GRPH + COPY（VM メニューの項目にもする。[spec.md](spec.md)）で、表示中の画面を 2 つの
PNG にしてホストのカレントディレクトリへ書く。ゲストは撮っているあいだ止まっている（ホスト世界で行う）。

| ファイル | 中身 |
| --- | --- |
| `<名前>###G.PNG` | グラフィック。640×400 の 4 ビット インデックスカラー。200 ライン（下の「ライン数の判定」）なら VRAM の 200 ラインを縦 2 倍にする。8 色モードでは B・R・G の 3 プレーン（A8000h・B0000h・B8000h）と、ゲストが書いたデジタルパレットの写しから 8 色。16 色モード（ポート 6Ah の bit 0。起動時は 8 色にしてあるので、ゲストの書き込みのトラップで追える）では E プレーン（E0000h）も読み、アナログパレットの写し（A8h = 番号、AAh = G、ACh = R、AEh = B）から 16 色。トラップした書き込みは実機にも通す |
| `<名前>###T.PNG` | テキスト。80 桁 × 25 行の文字コードと属性（A0000h・A2000h）を CG ROM のパターン（ポート A1h/A3h/A5h/A9h。§12）で 8×16 のマスに描く。色は属性の G・R・B の 8 色、文字のない画素はパレット番号 8 を tRNS で透明に。反転は塗りと抜きを入れ替え、下線は最下ライン、非表示は何も描かない |

ライン数の判定: ゲストがグラフィック GDC に CSRFORM（コマンド 4Bh）を書いていれば、その最初のパラメータの L/R（1 行の
ライン数 - 1）が 0 のとき 400 ライン。BIOS を通さずに GDC を設定するソフトは BIOS ワークエリアを変えないので、
ワークエリアだけでは 200 ラインのままに見える。ただし標準解像度のディスプレイの設定（ゲストのワークエリア 054Ch の
bit 6 が 0）では、BIOS は 200 ラインでも L/R を 0 にするので、400 ラインとは見なさない。CSRFORM を一度も見ていなければ
（起動直後や、BIOS がポートを通さないエミュレータ）、ワークエリア 054Dh の bit 2 で決める。パラメータのポート A0h は
描画でも頻繁に書かれるので、CSRFORM のコマンド（ポート A2h）を見てから最初の 1 バイトが来るまでの間だけトラップする。

`<名前>` は `-ss` の値（4 文字まで、英小文字は大文字に）、省略時はドライブ 0 のイメージのファイル名の
先頭 4 文字。`###` は 001 から 999 で、G と T の両方が存在しない最小の番号。

PNG は圧縮しない（deflate の stored ブロック。`src/core/png.c`。§12）。1 ファイル約 128KB。書き出しは
転送バッファ（64KB）に溜めてから DOS に渡す。

表示ページ: 撮るのは表示しているページ（ポート A4h）。VRAM の窓に見えているのは描画ページ（A6h）なので、違って
いれば撮る間だけ描画ページを合わせ、撮ったら戻す。2 つのページを切り替えながら描くソフトでは、描きかけや作業用の
ページが窓に出ている。

グラフィックチャージャー: ゲストがチャージャーを有効にしている間（ポート 7Ch の bit 7 が 1）は、モードによっては、
VRAM のどのプレーンの番地を読んでも同じ値（色との比較の結果など）が返り、プレーンの中身が読めない（§12）。
ホットキーは割り込みで拾うので、ゲストが描画の途中でも来る。そのまま撮ると 2 色の模様の絵になる（実機の報告。
§12）。チャージャーの状態は読み出せるとは限らず、書き込みを常にトラップして写しを持つのは、描画のたびに書かれる
ポートなので遅い機種で重い。状態を書き換えて撮ることもできない（モードを書くとタイルの書き込み位置が先頭に戻り、
ゲストの描画が壊れる）。そこで、撮る前に表示ページのプレーンを比べ、どれも同じ内容に読めたら撮るのを見送って、
ゲストを続けさせる。その間だけ 7Ch をトラップする（`vbm98.c` の `shot_hotkey`、ring 0 側は `vbm.h` の `shot_wait`）。
見送ったあと、次のどれかで撮る:

- ゲストが 7Ch に、チャージャーを止める値（bit 7 が 0）を書いた。その直後はプレーンの中身が読める
- 7Ch に何も書かれないまま、割り込み（ハードウェア割り込みと、ゲストの INT 命令）を 8 回ゲストへ渡した。
  チャージャーを使っていないゲストで、プレーンが同じに読めたのは絵がそうだったから（白黒 2 色の絵や、何も
  描かれていない画面）
- 見送ってから割り込みを 40 回渡した。チャージャーを有効にする値を書き続けて、止めないゲスト
- スクリーンショットのホットキーがもう一度押された

止める値が書かれた場合を除き、撮るときにもプレーンが同じに読めたら、その旨をログに残す（絵が正しいかどうかは
こちらでは見分けられない）。テキスト側は、撮るたびに属性の内訳（反転のセルの数、非表示のセルの数、0 行 0 桁の
属性）をログに残す。実機（PC-9801RA2）で、FreeDOS(98) をゲストにした画面が普通に見えているのに、テキストの絵が
95% 反転になったことがあり（原因は未確認。worklog の残作業 6）、属性の読み出しがどうなっていたかを次の報告で知る
ため。

見ていないもの: グラフィックの表示開始番地（常に VRAM の先頭から）、テキストの 20 行・40 桁
モード、属性の bit 4（縦線・簡易グラフィック文字）、点滅、テキストの表示開始番地。保存の成否はゲストの
画面に出さない（失敗だけコンソールに出る）。VM メニューから撮るときは見送れない（ゲストは止まったまま）ので、
メニューを開いた瞬間にゲストがチャージャーを有効にしていると、2 色の模様になることがある（ログには残る）。
EGC の拡張モードでは、VRAM の読み出しが EGC の内部の状態を書き換える（§12）ので、プレーンを比べる読み出しや
撮るための読み出しが、ゲストの描きかけの描画を乱しうる（起きるかは未確認）。

試験: `tests/boot/shotipl.S` が既知の文字（ANK・漢字・反転・下線・非表示）と色の帯を書き、開発用の
`-tick -shotat` で撮った PNG の画素を `tests/run_dos_tests.py shot` が確かめる（PC-98 の環境でだけ）。
文字の形はフォント ROM 次第なので、色と有無だけを見る。チャージャーについては、比較読み出しのモードにして回り
続ける IPL の変種 2 つ（1 周ごとに一瞬だけ止めるもの、止めないもの）と、チャージャーを使わずにプレーンが同じ
内容の絵を出す変種で、見送りと撮り方の 3 とおりを見る。確認済み（DOSBox-X、NP21/W。どちらも比較読み出しを再現し、
止めない変種では背景が白・帯が黒の絵が撮れる）。EGC の拡張モードの場合は試験していない。

## 18. EMM ドライバの下での動作（VCPI）

EMM386 などの仮想86モニタが常駐したホストでは、CPU は既に保護モード（ホストの DOS は EMM の仮想86タスク）で、
CR0 に触れない。VBM98 は VCPI 1.0 のクライアントになり、モード切替をサーバに頼む。1 本のバイナリで起動時に
判定する（[spec.md](spec.md) 2026-10-07）。変わるのは D1 の「ホストへ移る／戻る」の 2 手続きだけで、ゲストの
メモリは XMS から確保したままにする（§3 の 3 つ目の経路は使わなかった。下の「確かめたこと」）。

| 段階 | リアルモード（従来） | EMM の下（VCPI） |
| --- | --- | --- |
| 判定（`vbm98.c` の `check_v86`） | SMSW の PE = 0 | PE = 1。INT 67h AX=DE00h で VCPI の有無を見て、なければ止める |
| 準備（`mon_vcpi_setup`。`mon_init` の後） | — | AX=DE01h に、ホスト向けの 0 番ページ表（`monmem_build` の T_HOST。1MB 未満）と GDT の 3 項（セレクタ 38h〜48h）を渡す。サーバがページ表の先頭 1MB ぶん（とサーバ自身の分）と、サーバのコードセグメントの記述子を埋め、EBX に入口のオフセットを返す |
| ホストからモニタへ（`mon_enter`） | LGDT・LIDT・CR3・CR0 を自分で設定し、far jmp | 構造体（CR3、GDTR / IDTR の線形番地、LDTR = 0、TR = モニタの TSS、CS:EIP = `pm_start`）の線形番地を ESI に入れ、AX=DE0Ch で INT 67h。サーバがそれらを入れて飛ばしてくる。TR はサーバが入れるので `pm_start` の LTR は飛ばす |
| モニタからホストへ（`leave_pm`） | 恒等写像に戻し、CR0 の PG・PE を落として retf | 恒等写像（サーバが埋めた表）に戻し、SS を 1MB 未満の基底のセレクタに、DS を平坦なセレクタにして、戻り先の GS・FS・DS・ES・SS・ESP・EFLAGS・CS・EIP を 4 バイトずつ積み、EAX=DE0Ch でサーバの入口を 32 ビットの far call。仮想86 の `rm_back` へ戻る。LIDT は飛ばす（サーバが戻す。特権命令で実行もできない） |

成り立つ理由と前提:

- モニタのコード・データ・ページ表・横取り印のページは DOS の下位メモリ（640KB 未満）にあり、EMM の下でも線形 =
  物理（UMB は 640KB より上）。DE01h が埋める先頭 1MB の写像をホスト向けの表として使うので、サーバの入口を呼ぶ
  瞬間の写像はサーバと同じ。ゲスト向けの表（T_GUEST）はこちらのもので、A0000h〜FFFFFh は物理のまま見せる
- ホスト向けの表（サーバが埋めた先頭 1MB）で番地どおりでないページは、サーバが別のメモリ（UMB、EMS のページ枠）を
  写している所で、ホストとゲストで見える中身が違う。そこを指すベクタはホストの RAM として扱う（§6 の「ROM か
  どうかの基準」）。その範囲は起動時に `upper memory remapped by the EMM driver:` の行で表示する（動作報告の材料）
- モニタ自身は別名（物理 + 4MB）で見るので、下位 4MB の表がサーバのものでも動く（§3）
- ゲスト用メモリは XMS のロックが返す物理番地をページ表に書く。EMM の下でも XMS（HIMEMX）のブロックは物理的に
  連続していて動かないので、そのまま使える（確かめたこと）。VCPI のページ確保（AX=DE04h）は使っていない
- 割り込み: モニタの保護モードでは IDT はモニタのもの（従来どおり）。ホスト世界では EMM が受けて DOS に反射する。
  §7 の「切替を CLI で包む」はこちらの CLI が仮想になるので効かず、ホスト世界にいる間にゲスト宛ての割り込みが
  来ると EMM 側で処理される。いまは対策していない（下の「やっていないこと」）

やっていないこと: ホスト世界での割り込みの取りこぼし対策（VCPI の 8259 の対応付け AX=DE0Ah / DE0Bh は PC-98 では
IRQ0 = ベクタ 08h のままで、使う必要がなかった）、VCPI のページ確保を使う確保経路、EMS ページフレームとサウンド
BIOS の番地が重なる構成、横取り印のページを選ぶときにサーバが写し替えたページを避けること（ホストから全部 FFh に
読めるページを選んでいる。写し替えられたページがそう読めることがあるかは未確認）。

試験: `tests/run_dos_tests.py v86`。起動イメージの複製の FDCONFIG.SYS を同じ長さで書き換えて HIMEMX + EMM386
（NOEMS）を読み込ませ（`tests/dosenv.py`）、起動試験の IPL が INT 1Bh の往復とリセットを経て HLT まで動くことを見る。
確認済み（NP21/W、FreeDOS(98) の EMM386 2.26 NOEMS + HIMEMX）: 6 項目が通る（判定、VCPI 1.0 の検出、INT 1Bh の
往復、IPL が起こすリセット、HLT から DOS へ）。実イメージでも、リアルモードと EMM の下で `-tick -stopafter` の
同じ刻み数まで走らせて割り込みの内訳が一致した: イース2 は 6000 刻みで INT 1Bh 33 回・VSYNC 約 1800 回、
ソーサリアン（FM 音源）は 9000 刻みで INT 1Bh 16 回・VSYNC 約 700 回・IRQ12 約 1000 回で、止まった番地も同じ
領域。上の「割り込みの取りこぼし」はこの 2 本の範囲では症状として出ていない。
MS-DOS 5.00A（NEC）の EMM386.EXE は、引数なしでは VCPI を提供しないので、その下では案内を出して止まる（§12。
`run_dos_tests.py msdos`）。MS-DOS 6.20 の EMM386.EXE（`/UMB /HIGHSCAN /DPMI`、`DOS=HIGH,UMB`）の下では、E9000h からの
UMB に入れた試験用の常駐プログラムが割り込みを横取りしている状態で、起動試験の IPL が最後まで動く（確認済み:
NP21/W。同じ試験を 6.20 の起動ディスクで走らせたとき）。実機の EMM ドライバの下での結果は、利用者の報告による
（README の開発状況）。

## 19. 診断ログ（-log）

実機で動かないときの切り分けのため。ゲストが画面を使うので標準出力の診断は読めず、固まれば何も残らない。
そこで本体の表示をファイルにも書く（`src/dos/log.c`。[spec.md](spec.md) の `-log`）。

- 本体の表示はすべて `say()` を通す（標準出力と、開いていればログ）。起動時のホストの設定（スイッチ、ベクタ、IMR）、
  `-trace` の INT 1Bh の呼び出し、リセット・メニュー・停止・例外の記録、止まったときのダンプ（`dump_guest`:
  レジスタ、ベクタ表、PIC、割り込みの回数、直近のイベントと I/O）が残る
- 1 行ごとに DOS の書き込みと commit（AH=68h）を行い、ディレクトリ項目まで書き戻させる。ハングしたり外から
  リセットしたりしても、そこまでの行がファイルに残る（HOSTDRV で長さ 0 に見えた経験から。§12）。開くときは末尾に
  追記する
- 止まったとき（ゲストの例外、モニタ内の例外、開発用の `-stopafter`）の内容は、DOS も BIOS も通さず、テキスト VRAM に
  直接書く（`stop_report`。`say()` の出力先を `say_sink` で `ui_tty_put` に切り替える）。書くのはゲストから戻った直後、
  割り込みを許す前。実機（PC-9801BX）で、DOS を通した表示が例外の 1 行目の途中で止まり、何の例外かも読めなかった
  （利用者の画面写真。止まる原因は未確認）。DOS のコンソール出力にもホスト側の割り込みにも依らない経路にしておく。
  1 行目は理由で、ゲストの例外ならベクタ番号・エラーコード・番地を入れる。続けてレジスタと、例外の場所の命令バイト
  （CS:IP の 8 バイト前から 24 バイト）。命令バイトは例外を受けた ring 0 で、ゲストの写像を通して読んでおく
  （`fault_code`）。ホスト側からは、ゲストの RAM（XMS の塊）の外にある ROM の番地を、ゲストから見えるとおりには
  読めない。ここまではメモリの転送も使わない。そのあとの行はゲストのメモリを XMS ドライバ経由で読むので、
  ドライバが割り込みを許すことはありうる（未確認）。
  画面の下端を越えたぶんは捨てる（ログと、あとの出し直しには全部ある）
- そのあと割り込みを許し、ログをファイルに書いてから（`log_hold` で溜めておいたものを `log_release` で。ここで
  固まっても画面には内容が残っている）、画面の 0 行目に案内を出してキーを待つ（`stop_wait`）。待たずに進むと、
  ホストの画面を戻すときに内容が消える。キーが押されたらホストの画面を戻し、同じ内容を DOS を通して出し直す
  （次の項目）。標準出力がファイルに向いているときと、開発用の `-stopafter` では待たない
- 確度: 例外のベクタとエラーコードが 1 行目に出ること、内容がテキスト VRAM に直接書かれること、案内が出ることは
  確認済み（DOSBox-X、NP21/W。`con`）。割り込み禁止のまま最後まで書けるか、PC-9801BX でこれが読めるかは未確認
- 終了が決まってからの表示（終了の理由、止まったときのダンプ、起動できなかった理由）は、ホストの画面を戻した
  あとでもう一度画面に出す（`say_keep` / `say_again`。置き場は転送バッファの後ろ半分）。ゲストの画面が出ている間の
  表示はゲストの画面の上に出るので、終了時にホストの画面（起動前に控えたテキスト VRAM、§16）を戻すと上書きされて
  残らない。戻す前にも出すのは、戻す前に固まった場合に画面に残すため（上の項目）。標準出力がファイルに向いている
  ときは出し直さない（消えるものがなく、同じ行が 2 回入るだけになる）。ゲストが動いている間の表示（`-trace` の行、
  リセットの記録）は出し直さない。置き場の転送バッファをディスクの読み書きに使っているため
- ゲストが割り込み禁止のまま HLT で止まったとき（VM メニューが開く。§9）は、止まった所の様子をログにだけ書く
  （`halt_note`）: 上のダンプと同じ内容（レジスタ、CS:IP の 8 バイト前から 24 バイトの命令、ベクタ表、PIC、割り込みの
  回数、直近のイベント）に、スタックの先頭 8 語を足したもの。ソフトが自分で終了したのか、おかしくなって止まった
  のかは、止まった番地だけでは見分けられない。直近のイベントには、ゲストが最後に呼んだソフトウェア割り込みが
  番号・呼んだ番地・AX つきで残る。画面には出さない（メニューが使う。ゲストが出していた画面は、メニューの
  スクリーンショットで残せる）
- 画面への改行は CR LF で出す。DOS のコンソールは LF だけでは行を送るだけで、次の行が前の行の終わりの桁から始まる
  （確認済み: DOSBox-X、FreeDOS(98)、MS-DOS 6.20。実機の画面写真でも同じ形だった）
- 進み具合の表示（開発用の `-progress`）: 画面の右上（テキスト VRAM の 0 行目、58 桁目から）に
  `E0001 X0003 Ph I0 K0` の形で直接書く。E はゲストへ入った回数、X は最後にゲストから戻ったときの戻り値
  （`vbm.h` の `X_` の値）、P はホスト側のどの処理の中か、I と K はゲストの実行中に来たハードウェア割り込みと
  キーボード割り込みを数える 1 桁（ring 0 が書く）。DOS も BIOS も割り込みも使わないので、固まったときにも
  どこまで進んだかが画面に残る。P の字: G ゲストへ入る直前、H 戻った直後、h 割り込みを許したあと、
  a・r・w・s は INT 1Bh の処理（ゲストからの読み出し、イメージの読み書き、ゲストへの書き込み、終わり）、
  L・l は心拍のログの前後、K・k はキー待ちの前後、F・W は止まったときの表示とキー待ち。テキスト表示が
  消されていても見えるよう、書くたびにテキスト表示を ON にする（ゲストの画面の状態が変わるので、調べるとき
  だけ使う）
- 心拍（`-log <ファイル>,<秒>`）: `-tick` と同じ仕組みで IRQ0 をモニタの時計にし、指定の間隔で `X_LOGTICK` でホストへ
  戻って、ゲストの CS:IP・SS:SP・AX・FLAGS・IMR・割り込みの回数と、前回の心拍からのイベント（`evlog`。あふれたら
  最新の 32 件）をログだけに書いて（`log_line`。画面には出さない）すぐ戻る。固まったとき、最後の心拍までの位置と
  イベントの流れが分かる。`-tick` の制約（ゲストが IRQ0 を閉じていてもハードウェアでは開けておき、見せかけの
  マスクを返す）がそのまま付く
- 書かないもの: ゲストのメモリの中身、I/O の全記録（`-traceio` で指定したポートだけ `iolog` に残り、ダンプに出る）。
  ring 0 側はファイルに書けないので、心拍か停止のときにまとめて書く

試験: 起動試験に `-log B.LOG`（表示と同じ行がログにあること）、VM メニューの試験に `-log M.LOG,1`（心拍の行と停止の
ダンプがログにあること。停止からあとの画面の行が、同じ並びでログの末尾にあること）。確認済み（DOSBox-X、NP21/W）。
まとめて書く処理を外すと、ダンプがログに入らず 2 項目が落ちる。ログそのものは実機でも取れている（利用者の報告）。
起動試験は、IPL が最後に実行する CLI・HLT で止まった所の内容がログにあること（CS:IP の前の最後のバイトが FAh、
CS:IP が F4h、直近のイベント、スタックの行）と、画面には出ていないことも見る。確認済み（DOSBox-X、NP21/W）。

画面に残るものの試験（`con`）: 出力をファイルに向けずに本体を走らせ、DOS に戻ったあとのテキスト VRAM を試験用の
プログラム（`tests/boot/tvdump.S`）でファイルに書いて読む。終了の理由の行が画面にあること、起動前の表示が残って
いること、本体の行がどれも左端から始まることを見る。確認済み（DOSBox-X、NP21/W の FreeDOS(98) と MS-DOS 5.00A・6.20。
出し直しと CR を入れる前は、DOSBox-X・FreeDOS(98)・MS-DOS 6.20 のどれでも、終了の理由と左端の 2 項目が落ちた）。ほかの試験は出力をファイルで読むので、
画面でだけ起きることはこの試験でしか見えない。ゲストの例外で止まる場合は、特権命令を実行する試験用の IPL
（`tests/boot/faultipl.S`）で起こす。キーを待っている間の画面は、`-trace` を付けると本体が 0 行目と 1 行目をログに
写すので、それを読む（キーは開発用のキー列が答える）。

## 20. 仮想の DMA コントローラ

ゲストの DMA コントローラ（8237）へのアクセスはすべて横取りし、値は仮想のレジスタに持つ（`src/dos/vbm_r0.c`）。
実物のコントローラはホスト専用で、ゲストの読み書きは届かない。

- 理由: ゲストが書く番地はゲストの RAM の番地で、その RAM は拡張メモリ上にある（§3）。実物のコントローラにそのまま
  届くと、転送はホストの下位メモリの同じ番地に当たる
- 実物 1 個をホストとゲストで交代して使う（切替のたびに控えて書き戻す）形にしない理由: 8237 の番地と長さは読むと
  現在値が返り、書いた値（自動で繰り返すときに戻る値）は読み出せないので、控えを取りきれない。仮想にすれば控えが
  要らない。「読み出せない」は 8237 の一般的な説明の記憶に依っていて、資料では確かめていない（推測）
- 前提: ゲストの RAM がホストの下位メモリと別に確保されていること（[spec.md](spec.md)）

いまの範囲は状態の保持だけで、転送は起こさない。DMA で転送するソフトは、設定はできるが転送が始まらない。

| ポート | 書き込み | 読み出し |
| --- | --- | --- |
| 01h + 4n、03h + 4n | チャネル n の番地、長さ。下位・上位の順に 2 回 | 書いた値（転送が進まないので変わらない） |
| 11h | コマンド | ステータス。0 のまま（転送の終わりも要求も立たない） |
| 13h | 要求レジスタ（受けて捨てる） | FFh |
| 15h | マスクを 1 チャネルずつ（bit 1-0 がチャネル、bit 2 が 1 で閉じる） | FFh |
| 17h | モード（bit 1-0 がチャネル） | FFh |
| 19h | 上位・下位の切替を戻す | FFh |
| 1Bh | 初期化（全チャネルを閉じ、切替を戻す） | FFh |
| 1Dh | 全チャネルを開ける | FFh |
| 1Fh | マスクを 4 チャネル一括で | FFh |
| 27h・21h・23h・25h | チャネル 0・1・2・3 のバンク（番地の bit 16〜23） | FFh |
| 29h | バンクの繰り上がりの設定（bit 1-0 がチャネル、bit 3-2 が設定） | FFh |
| 0E05h + 2n | チャネル n の拡張バンク（番地の bit 24〜） | FFh |

- 割り当ての出典と確度は §12。横取りするのは表の番地だけ。参考実装は 01h〜1Fh を上位ビットを見ない形で登録して
  いるが、別名の番地（0101h など）は横取りしていない。実機で別名が効くかは未確認
- 起動時とリセット（§10）で、全チャネルを閉じ、ほかを 0 にする
- 実物のコントローラには読み書きしない。実物のチャネルのマスクも変えない
- ゲストがチャネルを開けたら（閉じていたものが開いたとき）、チャネル・モード・番地・長さをログ（§19）に 1 行書く。
  ゲストの画面を汚さないよう画面には出さず、開けた回数を終了時に表示する。書くのは ring 0 からホスト側へ戻った
  次の機会（INT 1Bh、心拍、停止など）なので、行に出る設定はその時点の値で、行の位置も開けた瞬間より後ろになる

確度: ゲストが書いた番地と長さを読み返せること、ゲストの書き込みの前後で実物のチャネル 1 の番地と長さが変わらない
こと、リセットでチャネルが閉じ直されることは確認済み（DOSBox-X、NP21/W。`tests/run_dos_tests.py` の `boot`。ポートを
横取りしない版では、実物のチャネル 1 がゲストの書いた値になって落ちる）。実機では未確認。
