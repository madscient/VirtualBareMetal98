### 2. ホストの調査（NP21/W と実機）

- MS-DOS 起動後の割り込みベクタ表のうち RAM を指すものは、起動時の表示（`redirected:` と `traced to their ROM entries:`）で
  分かる。エミュレータ上の FreeDOS(98)・MS-DOS 5.00A / 6.20・DOSBox-X の内蔵 DOS の分は design.md §12 にある
- シングルステップ追跡による ROM の入口探しは実装済み（[design.md](design.md) §6）。実機の MS-DOS 6.20 / Windows 98 の
  DOS（INT 09h と 1Ah を横取りしている。下の経緯の実機報告）で入口が得られるかは、次の報告のログで見る。得られない
  ベクタがあれば、起動時の `INT xxh enters the ROM at ...` の行（入口と認めなかった入り方）の有無で切り分ける。行が
  あれば design.md §6 の (a)〜(c) に当てはまらない横取りの形なので、その形を調べて足す。行がなければ、ハンドラが
  AX = FF00h では ROM を呼んでいない（追う回数の上限、機能番号の選び方を見直す）

### 5. V30 エミュレーション

[design.md](design.md) §14。`src/mon/v30_r0.c` に実装し、`tests/monprobe` の `g_v30_*` 8 断片で検証する（期待値は表）。
9 断片とも DOSBox-X（cputype=486）で期待値どおり。残り: CR4 の TSD を立てて RDTSC（0F 31 = INS reg,reg）を例外に
すること（Pentium 以降の実機向け。CPUID の有無の判定と、EMM の下での CR4 の戻しが要る）、ゲストが自前のハンドラを
持つときのゼロ除算の戻り番地の確認（試験未作成）、実イメージで V30 命令を使うものが見つかったときの確認。

### 7. EMM ドライバとの共存（VCPI）

実装済み（design.md §18）。1 本のバイナリで起動時に判定し（SMSW の PE と INT 67h AX=DE00h）、EMM の下では
VCPI 経由でモード切替する。ゲスト用メモリは XMS のまま（EMM の下でも XMS のロックが返す物理番地がそのまま使えた）。
NP21/W の FreeDOS(98) + HIMEMX + EMM386（NOEMS）で `run_dos_tests.py v86` が通る。残り:

| 項目 | 内容 |
| --- | --- |
| 割り込みの取りこぼし | ホスト世界にいる間の割り込みは EMM 側が受けてホストの IVT へ反射する。こちらの CLI は仮想なので、§7 の「切替を CLI で包む」手では防げない。イース2（60 秒）とソーサリアン（FM 音源、約 75 秒）をリアルモードと EMM の下で比べたところ、割り込みの内訳と INT 1Bh の回数が一致し、症状は出なかった（design.md §18）。症状が出るイメージが見つかったら、ホスト世界の滞在を短くするか EMM 側に割り込みを渡さない手段を探す（§13） |
| MS-DOS の EMM386 で VCPI を有効にする書き方 | MS-DOS 6.20 は `/DPMI` で VCPI が出る（NP21/W で確認。design.md §12）。利用者には README で案内している。残り: (1) MS-DOS 5.00A は `/DPMI` を受け付けるが VCPI は出ない。引数解析には `VCPI` という語との比較があるが、`/VCPI` も `VCPI` も組み込みに失敗する。書き方は分かっていない（マニュアルか引数解析の続きを読む）。(2) 6.20 の `/UMB /HIGHSCAN /DPMI` の構成は `msdos` の試験に入れた（起動ディスクが 6.20 のときだけ走る） |
| 確かめていない構成 | ほかの EMM ドライバ（LEMM、VEM486 など）が上位メモリのどこを写し替えるか（起動時の `upper memory remapped by the EMM driver:` の行で分かる）、EMS ページフレームとサウンド BIOS（`-sbrom`）の番地の重なり、MS-DOS 3.3C（XMS ドライバが付属しないので別途要る） |
| VCPI のページ確保 | XMS が使えない構成が出たら AX=DE04h の経路を足す（§3 の 3 つ目の経路） |

### 8. D88 形式のイメージ

形式で、配布されている MS-DOS のディスク（3.3C など）もこの形式のものがある。形式の中身は下のとおり記憶で書いて
いるので、着手の最初に資料で確かめて [disk-image-formats.md](disk-image-formats.md) に出典つきで書く。

| 項目 | 内容 |
| --- | --- |
| 形式の確認 | 記憶: ヘッダは 2B0h バイト（ディスク名 17、予約 9、書き込み禁止 1、媒体種別 1 = 00h 2D / 10h 2DD / 20h 2HD、ディスクの大きさ 4、トラックの位置表 164 個 × 4）。位置表が 160 個（ヘッダ 2A0h）の版もある。各セクタは 16 バイトのヘッダ（C・H・R・N、トラック内のセクタ数 2、密度 = 00h 倍密 / 40h 単密、削除マーク、ステータス、予約 5、データ長 2）にデータが続く。1 つのファイルに複数のディスクが連なることがある。出典を確かめ、参考実装（NP2kai の `diskimage/fd/fdd_d88.c`）と突き合わせる |
| 判定 | 決まった署名がない。ヘッダの「ディスクの大きさ」とファイルの大きさ、位置表の値（ヘッダの直後から始まり、単調で、ファイルの中に収まる）、最初のセクタのヘッダの整合で判定する。RAW と取り違えないことを試験で確かめる（RAW は大きさが 5 種に限られるので、先に D88 を試す順にする） |
| ディスクイメージ層 | `src/core/dimg.c` に `mount_d88` とトラックの読み込みを足す（`DIMG_FMT_D88`）。器は合う見込み: 位置表 164 個は `DIMG_MAX_TRACKS` と同じで、セクタごとの C・H・R・N・密度・削除マーク・ステータスは NFD と同じ持ち方ができる。トラックごとにセクタを順に読んで位置を数える（NFD r1 と同じ）。データ長が N と合わないセクタ、0 セクタのトラック（未フォーマット）、位置 0 のトラックの扱いを決める。書き込みはセクタのデータ部へそのまま。書き込み禁止はヘッダのフラグとファイルの属性の両方 |
| 複数ディスク入りのファイル | 最初の 1 枚だけを使うか、選ばせるか。選ばせるなら VM メニューのファイル選択に 1 段足す（外から見える振る舞いなので、決める前に利用者に聞く） |
| 媒体種別 | ヘッダの種別（2D / 2DD / 2HD）を `DIMG_MEDIA_*` に対応させる。1.44MB は種別がないので、2HD でセクタ長 512・18 セクタ以上なら 1.44MB とみなす（FDD 形式と同じ推定）かを決める |

| 利用者に見える所 | ファイル選択の一覧の拡張子に .d88（と .d77 / .d68 / .88d を入れるか）を足す。spec.md と README の対応形式の表、disk-image-formats.md を直す |

### 9. コードセグメントとデータセグメントの残り

本体は small モデル（コードが 1 セグメント、データが 1 セグメント）。どちらも 64KB までで、`tools/build16.sh` がリンクの
たびに残りを表示する（2026-10-10 の時点で、コードの残り 2,732 バイト、スタックに残る量 26,784 バイト）。
利用者の判断（2026-10-10、[spec.md](spec.md) の確定事項）: コード側は small のまま、関数を別のコードセグメントへ
出す（`far_section`）。medium モデルへの切り替えはしない。データ側は、移せるものを XMS へ出す。

**データ側**

- データセグメントには、初期値つきのデータ（8.5KB）、.bss（54.5KB）、スタックが同居する。スタックは上端から下へ伸び、
  使えるのは .bss の終わりまで。静的な置き場を足すと、そのぶんスタックが黙って減る。リンカが止めるのは残りが 768
  バイトを切ってから。`tools/build16.sh` で `min_stack`（16,384 バイト）を切ったら止めるようにした（値を残りより大きく
  すると止まることを確認）
- 実測（一時的に計測を入れた版。起動時に空きを決まった値で塗り、終了時に変わった所を探す）: DOSBox-X で 796〜822
  バイト、NP21/W の FreeDOS(98) で 782〜808、MS-DOS 6.20 の EMM386（UMB と常駐プログラムあり）で 730、FreeDOS の EMM386 で
  784。ヒープは使っていない。実機では未計測: ホスト側にいる間に来た割り込みは、ホストのドライバや常駐物がこの
  スタックの上で処理するので、使う量はホストの構成で変わる（どれだけ増えるかは未計測）。実機でまれに起きている原因不明の固まり（残作業 6 の表）と
  関係があるかは未確認（決めるには、終了時にスタックの使用量を出して、実機の報告で見る）
- .bss の大きいもの: `tvram_save` 16,384（ホストのテキスト画面の控え）、`monasm.S` の表 11,610（TSS と I/O 許可ビット
  マップ、IDT、GDT、モニタのスタック。ring 0 が使うので動かせない）、`imgs` 5,300、`save_code` と `save_attr` 各 4,000
  （メニューの間のゲストの画面の控え）、`entries` 2,800（ファイル選択の一覧）、`iotrap_buf` 2,048、ring 0 側の記録
  1,736、`cellpat` 1,280、`crc_table` 1,024
- 済み: `tvram_save` と `save_code`・`save_attr`（計 24KB）を XMS へ出した（`vbm.h` の `stash_write` / `stash_read`。
  ゲスト用メモリの後ろに `STASH_KB` ぶん確保し、VRAM と XMS のあいだを XMS ドライバに直接写させる。design.md §3）。
  スタックに残る量は 2,484 から 26,784 バイトになった
- 残り: ポインタで細かく触る置き場（`imgs` 5,300、`entries` 2,800、`iotrap_buf` 2,048、`cellpat` 1,280、`crc_table`
  1,024）は XMS には向かない。要るなら DOS から別に確保したメモリへ far ポインタで。ring 0 が使うもの（`monasm.S` の表
  11,610、ring 0 側の記録 1,736）は動かせない。終了時にスタックの使用量をログに出す手は未着手（実機でどれだけ使うかを
  知る材料になる）

**コード側**

内訳（リンクマップから。バイト）: libc 14,533、`vbm98.c` 12,873（うち `main` が 6,926。起動・実行のループ・終了の処理が取り込まれている）、
`dimg.c` 5,216、libgcc 4,891、`vbm_r0.c` 3,120、`fdbios.c` 2,763、`v30_r0.c` 2,370、`monasm.S` 2,322、`shot.c` 1,906、
`menu.c` 1,523、`mon.c` 1,472、`png.c` 1,450、`ui.c` 1,246、`mon_r0.c` 1,226、libi86 1,022、ほか。ring 0 で動くもの
（`_r0.c` の 3 本と `monasm.S`。計 9.0KB）は、モニタのコードセグメント 1 つに収まっていなければならない。

メモリモデルについて確かめたこと（gcc-ia16 6.3.0、`--target-help` と付属のライブラリの一覧）:

- あるのは tiny・small・medium の 3 つ。compact と large は無い（データを far で持つモデルが無い）。compact はコードが
  1 セグメントのままなので、あったとしてもコードの上限は変わらない
- medium（コードが複数セグメント、データは 1 つ）は、ライブラリとリンカスクリプトが付属している。関数はソース
  ファイルごとの別セグメントに入り、戻りは far、ファイルをまたぐ呼び出しはセグメントの再配置つきの far call になる
- small のままでも、関数を 1 つずつ別のコードセグメントへ出せる: `__far` と `__attribute__((far_section))` を付けた関数は
  別のセグメントに置かれ、far call で呼ばれる。そこから near の関数（libc など）を呼ぶ所は、コンパイラが中継の断片
  （`__ia16_far_call_thunk`）を通す。small 用の既定のリンカスクリプトがそのまま扱う。小さなプログラムで、コンパイル・
  リンクし、DOSBox-X で走らせて確かめた（本体には当てていない）

「浮く量」は、リンクマップにある部品の大きさからの見積もりで、実際に外して確かめてはいない（未検証）。

| 減らし方 | 浮く量 | 値段 |
| --- | --- | --- |
| 書式の整形を自前にする（`say()` と `menu.c` の `sprintf` が使う `%s` `%c` `%u` `%d` `%X` と桁指定、`l` 付きだけを持つ小さな整形器に替える） | 約 13KB（libc の `svfiprintf` 4.4KB、`locale` 2.4KB、`mbtowc_r` 1.6KB、`wctomb_r` 0.7KB、libgcc の 64 ビット除算 `_udivdi3`・`_umoddi3` 4.5KB ほか） | `log.c` と `menu.c` の 2 箇所。使っている書式を全部洗い出して、整形器の試験をホスト OS 上に足す。表示は全試験が読んでいるので、壊せば試験で分かる |

### 10. ストレージの切り離しと、仮想の DMA コントローラ

利用者の判断（2026-10-09）。[spec.md](spec.md) の確定事項。割り込みも DMA も、いまは実物 1 組をホストとゲストが時間で
交代して使っていて、取り合いの手当てがなかった。A と、B の段階 1 まで実装済み。

**A. ホストのストレージをゲストに見せない**（実装済み。design.md §6 の「ホストの IRQ」。実機の結果待ち）

| 項目 | 内容 |
| --- | --- |
| いまの動き | ゲストの割り込みマスクの初期値はホストの値のまま。ホストの RAM のハンドラを指す IRQ のベクタは「EOI を出して戻る」印に向けてあるので、ゲストの実行中に来たホストの装置の割り込みは、装置側の要求が片付かないまま消える。割り込みコントローラは立ち上がりで反応するので、以後その IRQ が来なくなる |
| やること | design.md §6 の規則 3 の後半（「それが IRQ のベクタなら、ゲストの割り込みマスクの初期値でその IRQ を閉じる」）を実装する。印に向けた 08h〜17h のベクタに当たる IRQ を、ゲストのマスクの初期値で閉じる。閉じている間に来た割り込みは保留され、ホストに戻ってマスクを戻した時点でホストのハンドラに届く。ゲストが自分でハンドラを置いてマスクを開けたら、ゲストの設定に従う |
| 確かめること | PC-9801BX（SCSI のボード、IRQ5 が開いていてベクタ 0Dh が RAM）で、ゲストを動かしたあとのディスクアクセスが止まらなくなるか。v0.1.4 の止まった画面の `hardware interrupts seen` に `0D=` があるかで、原因がこれかどうかが先に分かる |
| やらないこと | ディスクのボードの I/O ポートをゲストから触れなくすること（ボードの種類ごとにポートが違い、一覧を決めきれない） |

**B. 仮想の DMA コントローラ**

方針: ゲストの DMA コントローラへのアクセスはすべて横取りし、値は仮想の状態として持つ。実物のコントローラはホスト専用にし、
ゲストとは共有しない（状態の控えや書き戻しをしないで済む）。データ転送はモニタが代行する。

| 段階 | 内容 | 値段 |
| --- | --- | --- |
| 1. 状態だけ（実装済み。design.md §20） | 8237 のポート（チャネルごとの番地と長さ、モード、マスク、ステータス、バイト順の切替）とバンクレジスタを横取りして、仮想のレジスタに保持する。読み出しは仮想の値を返す。実物には書かない。ゲストがチャネルのマスクを開けて転送を始めようとしたら、チャネル・モード・番地・長さをログに出す（どのソフトが DMA を使うかを知る材料）。この段階では転送は起きないので、DMA の PCM は鳴らないが、ホストのメモリは壊れない | 中の小。ring 0 側に部品 1 つ。試験は起動試験の IPL から設定して読み返し、ホスト側で実物のレジスタが変わっていないことを見る |
| 2. 転送の代行 | ゲストが転送を始めたら、モニタが実物のそのチャネルを代わりに設定して、実物の装置（音源ボード）との転送を起こす。番地はゲストの番地から実物の番地に直す（ゲストの RAM は拡張メモリ上の連続した 1 塊なので足し算）。実物のコントローラが届かない番地なら、下位メモリに中継の置き場を取り、再生なら先に写し、録音なら終わってから写し戻す。自動で繰り返すモードは、区切りごとに次のぶんを写す。ゲストが読む現在の番地・長さ・ステータスは、実物の値をゲストの番地に直して返す。終了・リセットのときは、代行で開けたチャネルを閉じる | 中〜大。機種ごとの届く範囲、区切りの検出（割り込みかポーリングか）、ホストが同じチャネルを使う場合の扱いを決める必要がある |

設計の前に確かめること（どれも記憶で書かない）:

- PC-98 の 8237 のポートの割り当て、バンクレジスタの番地と幅、バンクの繰り上がりの設定、機種による違い。出典は
  参考実装（NP2kai の `io/dmac.c`）と資料
- DMA で PCM を鳴らす音源ボード（PC-9801-118、WSS 系など）が使うチャネルと、転送の区切りの知らせ方
- 試験の環境で DMA の PCM を再現できるか（NP21/W・DOSBox-X の音源の実装）
- 段階 2 で外から見えるもの（代行を常に行うか、オプションで有効にするか）。決める前に利用者に聞く
- 8237 の初期化（1Bh）が番地・長さ・切替をどうするか（design.md §12 に推測で書いてある）、番地と長さ以外の
  レジスタを読んだときの値
- 実物のチャネルのマスクの扱い。いまは実物に一切触れないので、ゲストが実物の装置（音源ボードのポートは横取りして
  いない）に転送の要求を出させたとき、実物のそのチャネルが開いていれば、ホストが最後に設定した番地で転送が起きる。
  ホストがチャネルを開けたままにしている場合があるかは未確認（常駐物や BIOS が転送のあとチャネルを閉じるかを、実機で
  ゲストの起動前にマスクの状態から見る。ただし 8237 のマスクが読み出せるかも資料で確かめる）
- 別名の番地（参考実装は 01h〜1Fh を上位ビットを見ない形で登録している）が実機で効くか。効くなら横取りの範囲に足す
- 段階 1 のログの行（`guest opened DMA channel`）が実機の報告に出てくるか。出てきたソフトと設定が、段階 2 の対象と
  優先順位を決める材料になる

利用者の見立て: DMA の使い道は PCM が多い。FDC を BIOS を通さず直接操作するゲームは少ない（ドライブの種類が機種ごとに
違い、直接操作しても正しく制御できるか分からないため）。FDC の代行は引き続き対象外（下の「見送った提案」）。

### 11. FD イメージを XMS にオンメモリで持つ（あとで検討）

利用者の方針（2026-10-10）。検討はまだ。動機は実機の報告: ディスクを読む間はゲストが止まる作りなので、FM 音源の音が
途切れる。イメージを RAM ディスクに置くと途切れなかった（残作業 6 の表）。いまは `-fdd0` / `-fdd1` のファイルから、
INT 1Bh のたびに必要なセクタだけ読んでいる（design.md §8）。

| 項目 | 検討すること |
| --- | --- |
| 置き場と量 | XMS に 1 枚ぶんずつ（2HD で 1.2〜1.4MB、NFD の詳細形式はそれ以上）。ゲスト用メモリ 668KB と合わせて、拡張メモリの要件が 1 枚あたり 1.3MB 前後増える。足りない機種のために、ファイルから読む今の経路は残す（切り替えの条件: 自動か、オプションか。外から見える値なので決める前に聞く） |
| 読み込み | 起動時かディスク交換時に、ファイルから XMS へ写す（転送バッファ 64KB を経由）。1.2MB で数秒かかる機種がある。進み具合の表示が要るか |
| 読み出しの経路 | `fdbios.c` はイメージ層（`dimg.c`）の読み書き関数を関数ポインタで呼ぶ（`dimg_io`）。XMS 版の `dimg_io` を 1 組足せば、`src/core/` を変えずに済むか。XMS の転送は偶数長・1MB 未満の seg:off 相手なので、転送バッファを中継にする |
| 書き込み | ゲストの書き込みは XMS 上の写しに入る。ファイルへいつ書き戻すか（セクタごとに即時か、終了時か、ディスク交換時か）。即時なら音は途切れるが、今と同じ。終了時にまとめるなら、固まったりリセットされたりしたときに失う |
| 効果の見積もり | ディスクを読む間ゲストが止まるのは変わらない。XMS の転送はファイルの読み込みより速いが、ホスト世界への往復は残る。先に、INT 1Bh 1 回あたりの時間の内訳（ファイルの読み込みと、それ以外）を測ってから決める |
| 試験 | `img` / `fdb` の試験を XMS 版の経路でも走らせる。書き戻しの時機の試験 |

### リリースの手順

1. `src/dos/vbm98.c` の `VBM98_VERSION` を `x.y.z` にしてビルドする
2. ホスト OS 上の試験と、DOS 上の全試験を DOSBox-X と NP21/W の両方で通す
3. `vx.y.z` の題でコミットし、同じ名前のタグを打って、ブランチとタグを push する
4. `build/dos/` の `VBM98.EXE` と `VBM98.DOC`、リポジトリの `README.md` と `LICENSE` を `build/release/` に写し、zip にする。
   zip は Windows の `tar.exe`（`%SystemRoot%\System32`）の `-a -c -f` で作る。Git Bash の `tar` は同じ引数で tar 形式の
   ファイルを作るので使わない。上げる前に、zip として開けることと、中の `VBM98.EXE` と `VBM98.DOC` の版を確かめる
5. `gh release create vx.y.z --verify-tag` で、zip と `VBM98.EXE` を付けて公開する。リリースノートには、v 前回からの変更、
   実機での結果（利用者の報告）、実機では未確認であることを書く
6. `VBM98_VERSION` を `x.y.z+` に戻してビルドし、経緯にリリースを記録してコミット、push する

### 試験が誤りを捕まえることを確かめた方法

ソースの作業用コピーに誤りを 1 つ入れて試験を走らせ、落ちることを見た。使ったスクリプトは
残していない。試験を大きく変えたら、同じ確認をやり直す。
誤りを入れて走らせている間に止められると、ソースに誤りが残る。入れる前の中身を控えておき、終わったら `git diff` で、意図した変更だけが残っていることを見る。長い実行は 1 つずつに分け、時間切れで止められないようにする。

| 対象 | 入れた誤り | 結果 |
| --- | --- | --- |
| ディスクイメージ層（ホスト OS 上） | NFD r1: リトライぶんのデータを数えない（トラック読込、マウントの 2 箇所）／特殊読み込みのデータ長の位置をずらす／特殊読み込みぶんを飛ばさない。NFD r0: トラック数を 1 減らす／DDAM を落とす。NFD: 1.44MB を 2HD と見なす。FDD: 位置表の要素の大きさを変える／位置 0 をデータなしと見なさない／実体化しても位置表を書き換えない／1.44MB の判定をずらす。一様形式: 片面でもヘッド数 2 で位置を計算する。FDI: サイズの整合を見ない／ヘッダ長を無視する。書き込み禁止を見ない。複数通りのデータの 1 通り目にしか書かない。RAW: 2HC のセクタ数を変える | 17 通りとも、該当するケースが落ちた |
| ディスクイメージ層（DOS 上） | NFD r0 の位置表の位置を `unsigned` で計算する | ホスト OS 上は全件通過、DOS 上は NFD r0 の 6 件が落ちた |
| モニタ核 | ゲートを DPL=0 にする／ゲストを IOPL=0 で走らせる／エラーコードの有無の判定を逆にする | 3 通りとも落ちた。応答なしにはならなかった |
| モニタ核（2026-10-06 の追加分） | 入口で下位 4MB をゲスト向けの写像に切り替えない／トラップした IN AX,DX をバイトとして扱う／DPL=0 のゲートへの INT n を別のベクタへ反射する | 3 通りとも落ちた。1 つ目はゲスト用メモリの試験で応答なしになり、時間切れで検出された |

| モニタ核（HLT と横取り印） | 横取り印の表を違う番地で照合する／HLT で待つ前に IP を進めない | 2 通りとも応答なしになり、時間切れで検出された（FAIL 行は出ない）。前者はリセットベクタの HLT が本物の HLT として待たれ、後者は割り込みのたびに HLT へ戻る |
| ROM の入口の追跡（`romtrace.S`） | far call なら FLAGS の語を見ずに入口と認める／NEC の MS-DOS の INT 1Ah の入り方（design.md §6 の (c)）を認識しない | 前者は `hook` が応答なしになり、時間切れで検出された（DOSBox-X）。後者は `msdos` の 2 項目が落ち、INT 1Ah は印のまま起動した（NP21/W + MS-DOS 5.00A）。追跡そのものを入れる前は `hook` の 09h・1Ah の 2 項目が落ちた |
| ホストの IRQ を閉じる（DOSBox-X、`hook`、2026-10-09） | ホストのハンドラが受け持つ IRQ を閉じない／キーボードの IRQ も閉じる | 前者は 1 項目が落ちた。後者は、最初の試験では落ちなかった（試験用の常駐プログラムのキーボードの横取りは入口を追跡できてしまい、閉じる対象にならない）ので、追跡できない形の横取り（`HOSTTSR.COM K`）を足して 1 項目が落ちるようにした |
| 仮想の DMA コントローラ（`boot`、2026-10-09） | DMA のポートを横取りしない／リセットでチャネルを閉じ直さない／番地と長さの上位バイトを読み出しで返さない／バンクを違うチャネルに入れる | 4 通りとも落ちた（順に 3・1・1・1 項目）。1 つ目では、ホスト側で読んだ実物のチャネル 1 が、ゲストの書いた番地 1234h・長さ 0FFFh になった（DOSBox-X と NP21/W の両方で見た。あとの 3 つは DOSBox-X だけ） |

| リアルモードへ戻ったときの CPU の状態（`mon`、2026-10-10） | 戻すものを 1 つずつにする（`mon_rmfix`。試験の中で切り替える） | 何も戻さないと FS・GS は 0 になり、32 ビットのレジスタの上位の印は 6 つとも消え、GDTR はモニタのものを指したままになる。FS・GS だけ戻すと、その 2 つだけが残る。レジスタだけ戻すと上位の印 6 つだけが残る。GDTR・CR3 だけ戻すと GDTR だけが戻る。DOSBox-X と NP21/W で同じ。PE を落とす手順と限界は、どちらのエミュレータでも違いが出ない（確かめられない） |
| EMM ドライバが写し替えたページの扱い（NP21/W + MS-DOS 6.20、`msdos`、2026-10-10） | E8000h 以上を無条件に ROM とみなす（直す前の動き）: ベクタの判定だけ／入口の追跡だけ | どちらも 20 項目のうち 6 項目が落ちた（起動試験の IPL が途中で止まり、時間切れ）。前者は `traced` の行が空になり、後者は `1A=E902:0120(a)`（常駐プログラムの中の番地）になった |

## 経緯

### 2026-10-05

- 要件の提示を受けた。リポジトリは空、16 ビット向けのビルド手段なし
- 4 形式の資料を取得。NFD は配布元のテキストが壊れており、r1 のみ無傷版を別途入手
- 読み比べのため NP2kai のイメージ読込部と FDD BIOS 部を参照した
- 確認した結果: 初版はリアルモード専用、ホストへの切替口は抽象化（確定）
- 実装言語を尋ねたところ「gcc-ia16 は使えないか」と打診された。調べた結果:
  - 公式配布は Ubuntu の PPA と DOS 版。Windows ネイティブ版は公式にはない
  - 開発機には WSL があり、Ubuntu 側に PPA の登録だけがある（本体は未導入）
  - 生成コードは 80286 までの 16 ビット、メモリモデルは tiny / small / medium
  - データが near の 64KB に限られる点について: ディスクイメージ層の常駐データはイメージ 1 枚あたり
    2,792 バイト（ホストの gcc での `sizeof(dimg)`）と共用の作業領域 416 バイトで、4 台ぶんでも
    約 12KB。16 ビット向けに実際にビルドして確かめるのは導入後
- コンパイラに依存しない部分としてディスクイメージ層を先に実装し、ホスト OS 上で検証した
- gcc-ia16 の導入で `apt install gcc-ia16-elf` が「パッケージが見つからない」で失敗した。
  原因は PPA が Ubuntu 18.04 向けの配布をやめていたこと（18.04 向けの索引が空。20.04 / 22.04 / 24.04 向けは配布中）
- 20.04 向けのパッケージ 4 つ（binutils-ia16-elf、gcc-ia16-elf、libnewlib-ia16-elf、libi86-ia16-elf）を
  索引のハッシュと照合したうえで 18.04 上に root なしで展開し、動くことを確かめた。
  binutils は同梱の共有ライブラリを `LD_LIBRARY_PATH` で指す必要がある
- この状態で確かめたこと: DOS 実行ファイルの生成、`__far` と DOS 呼び出しのコンパイル、
  `src/core/` のコンパイル（text 5,302 バイト）、付属アセンブラでの 16/32 ビット混在と特権命令のアセンブル
- printf を使う最小のプログラムが 24KB になった。DOS 側では標準入出力ライブラリに頼らない出力を用意する
- アセンブリは Intel 記法に決まった（確定）。付属アセンブラの Intel 記法で、16 ビットコード内の
  32 ビット版 LGDT / LIDT は `lgdtd` / `lidtd` と書く（`fword ptr` を付ける書き方は通らない）
- DOS の実行環境として DOSBox 0.74-3 と NP21/W（FreeDOS(98) の起動イメージ、ホストのフォルダを
  ドライブとして見せる HOSTDRV、エミュレータを終了させる PWOFF つき）が用意された。
  DOSBox 0.74-3 は PC-98 を再現しないので、機種に依らない範囲の確認に使う
- 試験プログラムをホスト OS と DOS の両方でビルドできる形に直し、DOS 用の入出力層を書いた。
  DOSBox を画面なしで起動してバッチを流し、結果ファイルを回収する形で 39 件が通った（約 80 秒）
- DOS 上の試験が 16 ビット固有の誤りを捕まえることを確かめた。位置の計算を `unsigned` で行う
  誤りを入れると、ホスト OS 上は全件通過、DOS 上は NFD r0 の 6 件が失敗した。
  同じ誤りを型変換なしで書いた場合は、ホスト OS 側のコンパイル時の警告で先に止まった
- モニタ核の最小版を書いた。アセンブリはモード切替と例外の入口・出口だけにし、判断は ring 0 で
  動く C に任せる構成にした（design.md の D8）。DOSBox 上で 25 項目が通った
- その過程で分かったこと:
  - gcc-ia16 の通常のコードは保護モードで動かない。32 ビット値の読み込みに LES を使うなど、
    セグメントレジスタを値の置き場にする。モニタ内で一般保護例外になり、エラーコードが
    「ゲストの IP の値」だったことから判明した。`-mprotected-mode` で解消した
  - ring 0 の C から C ライブラリやコンパイラの補助関数を呼ぶのも同じ理由で避ける。
    ビルドに外部参照の検査を入れたところ、構造体の代入が `memcpy` の呼び出しになっているのを
    その場で捕まえた
  - gcc-ia16 は ES を「呼ばれる側が保存するレジスタ」として扱う。モード切替の関数が ES を
    壊していたため、呼び出し側の変数（文字列へのポインタ、セグメント値）が化けた
  - 最初の版は DOSBox が応答しなくなった。上の 2 点を直したあとは再現していないが、
    どちらが応答なしの直接の原因だったかは切り分けていない
- 切り分けには、モニタ内で例外が起きたときにスタックの内容を控えて返す仕組みが効いた。
  これは `mon_panic_get` として残してある
- モニタ核の試験が誤りを捕まえることを確かめた。ゲートを DPL=0 にする、ゲストを IOPL=0 で
  走らせる、エラーコードの有無の判定を逆にする、の 3 通りでいずれも試験が落ちた
- MS-DOS Player（コンソールで DOS プログラムを直接走らせるもの）も置かれていたが、標準入出力を
  パイプにして起動すると引数なしでも戻らなかった。原因は調べていない。DOSBox で足りたので使っていない
- 別のマシンで続けられるように、環境の準備手順を [setup.md](setup.md) に、残作業と引き継ぎメモを
  この文書に、INT 1Bh について読み取ってあった事実を [design.md](design.md) §8 に書いた。
  それまでは開発機の上にしかなかった情報である

  開き、窓を撮ると、0Bh（KAC モード ON）だけが写真と同じ崩れ方になった。参考実装では、KAC が ON だとテキストの
  2 バイト目の判定が消える（design.md §12）。ゲームが KAC を ON にしたまま走っていて、そこへホットキーが来た形。
  68h への書き込みをトラップして写しを持ち、メニューの間だけ OFF にして戻すようにした（design.md §9）。直した版で

## 見送った提案

| 提案 | 見送った理由 | 見直す条件 |
| --- | --- | --- |
| ホスト側もすべてアセンブリで書く | イメージ解析と UI を実機／エミュレータ上でしか検証できなくなる | — |
| C コンパイラに Open Watcom を使う | gcc-ia16 の打診を受けて保留。gcc-ia16 はホスト検証用の gcc と同じ方言で書ける | gcc-ia16 で DOS 向けのビルド・リンクが成立しなかった場合 |
| モニタ核を NASM で書く | gcc-ia16 付属のアセンブラで必要な命令がアセンブルできると確認できた。ツールが 1 系統で済む | 付属アセンブラの記法や機能で困る点が出た場合。その際は NASM のオブジェクトをリンクできるかを先に試す |
| `-sbrom` でサウンド BIOS の INT D2h も登録する | IPL がヘッダ（CC000h + 2E00h）をどう読んで登録するかが資料から読み取れず、推測で書くと誤った登録になる。ROM を見せるだけで足りるアプリを先に対象にした（design.md §12・§15） | 登録が要るアプリが見つかり、手順を資料か実機で確かめられたとき |
| 18.04 に 20.04 向けパッケージを依存関係を無視して入れる | パッケージ管理が不整合な状態になる。展開するだけで動くと分かったので不要 | — |
| イメージ全体を起動時にメモリへ読み込む | 1 枚 1.2MB 前後 × ドライブ数の拡張メモリが要る。書き戻しの時機という別の問題も生む | 見直し中（2026-10-10、残作業 11）。実機で、ディスクを読む間 FM 音源が途切れる報告があり、RAM ディスクに置くと途切れなかった |

| 起動時にテキスト VRAM を両面 8KB 全部消す | 属性面の末尾にメモリスイッチがある。見えている 4000 バイトで足りた | ゲストが表示開始番地を変えて残りの領域を見せる場合（そのときも末尾 32 バイトは避ける） |
